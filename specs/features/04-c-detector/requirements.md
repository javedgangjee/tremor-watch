# Feature 4 requirements: C detector and the PADS match

## From the project documents

1. The C detector follows reference/plain_detector.py step for step, and it counts as correct only while it matches the toolbox. This comes from CLAUDE.md, the opening of the plan, and the plan's Build order step 4.
2. The C detector uses 32-bit floats. This comes from the notes under the plan's Detector recipe section, Build order step 4, and specs/tech-stack.md.
3. The C detector uses KISS FFT for the 400 point and the 200 point FFT, on the laptop and on the watch. It never pads to a power of two. KISS FFT has a BSD licence, and its commit is pinned. This comes from the Detector recipe section, specs/tech-stack.md, and the roadmap entry for feature 4.
4. The C detector takes its fixed numbers from core/detector_tables.h and never rebuilds them. Only the detector's C file includes the header, because the header holds static arrays. This comes from the Detector recipe section and the roadmap entry for feature 4.
5. The C detector does the eight steps of the Detector recipe for one window of 400 readings on three axes in degrees per second. It builds the fine spectrum, builds the coarse spectrum, groups the coarse spectrum into 15 bands, turns the bands into 12 numbers, scores the window, checks the peak, checks that the arm is at rest, and gives the answer. Where the toolbox's comments and its code disagree, it follows the code. This comes from the Detector recipe section.
6. The C detector gives the arm at rest answer as its own output, together with the tremor answer, the probability, the low-frequency sum, the peak frequency, and the 12 numbers. This comes from the Detector recipe section and the W line in the plan's USB recording section.
7. The code in core/ includes no ESP-IDF headers, allocates no memory at run time, gives every buffer a fixed size, builds with -ffp-contract=off, and builds as a plain C library on the laptop. This comes from the plan's Shared C library section and specs/tech-stack.md.
8. A few hundred test windows are saved in tests/ with the toolbox's answers and detector numbers, and they include windows close to each cut-off. This comes from Build order step 5 and the Repo layout section.
9. On the saved windows, the 12 numbers and the probability agree with the toolbox within 0.0001. The answers agree on every window, except where the toolbox's probability sits within 0.0001 of its cut-off, its low-frequency sum sits within 0.01 percent of 50, or its two largest peak steps differ by less than 0.01 percent. This comes from Build order step 5.
10. The laptop build includes replay, a command-line program that reads a PADS file and prints its own answer for every window. Recording input comes in feature 10. This comes from the plan's Shared C library section and the roadmap entries for features 4 and 10.
11. Replay converts PADS rotation from radians per second to degrees per second as the toolbox's own function does, cuts the first half second, and runs at 100 readings a second with no conversion. This comes from the plan's Test data section.
12. The same rule as in item 9 runs through replay on every PADS file. This full test needs the toolbox, so it runs before each release and not on every commit. This comes from Build order step 6 and specs/tech-stack.md.
13. A match report shows the C detector agreeing with the toolbox on every PADS file, with the largest difference in the probability. This comes from the plan's What you deliver section and the roadmap entry for feature 4.
14. The C answers must match the committed PADS windows and counts in reference/results/. This comes from Build order step 2 and specs/tech-stack.md.
15. The C unit tests use Unity and run on the laptop through CTest. This comes from specs/tech-stack.md.
16. Nobody retrains the detector or changes its stored numbers. This comes from CLAUDE.md and the opening of the plan.
17. Two new tests give tools/gen_tables.py a model whose feature names are not mfcc_1 to mfcc_12 and a classifier that is not a logistic regression with one row of 12 weights. Each test checks that the script stops and writes no file. This comes from the roadmap entry for feature 4.
18. This feature decides whether the C scoring step runs in 64-bit or 32-bit floats. This comes from the roadmap entry for feature 4.
19. New Python code follows the user's Python rules, and the Python tests use pytest in the reference venv when they need the toolbox. This comes from specs/tech-stack.md.

## Not covered by the project documents

Each item below is a choice that the build spec and the existing code leave open.

20. The scoring step runs in 64-bit doubles, and every step before it runs in 32-bit floats. The float32 run of plain_detector.py does the same, because numpy turns the 32-bit numbers into 64-bit values when it subtracts the 64-bit means. So the probability and the cut-off test are 64-bit. The low-frequency sum is also a 64-bit value, because plain_detector.py adds the 32-bit steps and then multiplies the sum by 0.25 as a Python float. The watch chip has no hardware for doubles, but the scoring step is only 12 multiplies, 12 adds, and one exp, and feature 8 measures the run time. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

21. KISS FFT is pinned to its release tag 131.2.0, which is commit 7bce4153c6bc8aba2db0e889e576f9d00505cbe1 of github.com/mborgerding/kissfft from 11 September 2025. The newer commits on its master branch date from October 2026 and are not in a release. The files kiss_fft.c, kiss_fft.h, kiss_fftr.c, kiss_fftr.h, _kiss_fft_guts.h, kiss_fft_log.h, COPYING, and LICENSES/BSD-3-Clause are copied unchanged into core/kissfft/. KISS FFT uses its default float type. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

22. KISS FFT never touches the heap. The detector sets up both FFT configurations in fixed static buffers in det_init(). KISS FFT builds with KISS_FFT_MALLOC and KISS_FFT_FREE set on the compiler command line so that they return a null pointer and do nothing, and the source files stay unchanged. The sizes 400 and 200 split into the factors 4, 2, 5, 5 and 4, 5, 5, so KISS FFT never needs its temporary buffer. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

23. Unity is pinned to its release tag v2.6.1, which is commit cbcd08fa7de711053a3deec6339ee89cad5d2697 of github.com/ThrowTheSwitch/Unity. The files src/unity.c, src/unity.h, src/unity_internals.h, and LICENSE.txt are copied unchanged into tests/unity/. Unity has an MIT licence. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

24. The detector is core/detector.h and core/detector.c. The header defines DET_WINDOW_LEN (400), DET_AXES (3), and DET_MFCC_COUNT (12), the result type det_result_t, and the functions `bool det_init(void)` and `void det_run(const float window[DET_WINDOW_LEN][DET_AXES], det_result_t *out)`. det_result_t holds `float mfcc[12]`, `double prob`, `double below`, `float peak_hz`, and the three answers `logreg`, `at_rest`, and `tremor` as `bool`. The detector keeps its work buffers in static memory, so only one task calls it, which is the pipeline task. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026. The header also declares `void det_decide(det_result_t *r)`, which sets the three answers from `prob`, `below`, and `peak_hz` and leaves those three alone. det_run() calls it last. It makes the same tests in the same order as before, so the outputs stay the same bit for bit. The model says yes when the probability is at least the cut-off, the arm is at rest when the low-frequency sum is 50 or less, and the peak passes from 3 to 7 Hz with both ends included. The saved windows never land on a cut-off, so test_detector also calls det_decide() with each cut-off exactly and with the next number on either side. The user asked for this fix on 27 October 2026.

25. The laptop build uses CMake. A CMakeLists.txt at the repo root adds core/ and tests/. core/CMakeLists.txt builds the library tremor_core and the program replay, and tests/CMakeLists.txt builds Unity and the C tests and registers them with CTest. The build folder is build/, and .gitignore leaves it out. The ESP-IDF component setup for core/ comes in feature 7 with the firmware base. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

26. The project's own C files build with `-std=c11 -Wall -Wextra -Werror -pedantic -ffp-contract=off`, which are the flags feature 3 used for dump_tables.c. The KISS FFT files build with `-std=c11 -ffp-contract=off` and without -Werror, because they are third-party code that stays unchanged. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

27. "The answers" in item 9 means the tremor answer and the arm at rest answer. A window that meets any of the three conditions in item 9 is near a cut-off, and both of its answers may differ. "Within 0.0001 of its cut-off" means a distance of 0.0001 or less, and "within 0.01 percent of 50" means a distance of 0.005 or less. The two largest peak steps differ by less than 0.01 percent when the largest minus the second largest, divided by the largest, is below 0.0001. These steps are the two largest values of the fine spectrum between 1 and 25 Hz, both ends included. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

28. The toolbox does not output its fine spectrum, so the tests compute it with scipy welch called with the same arguments as the toolbox's extract_spectral_domain_features. The tests check that this spectrum's largest step is at the toolbox's own peak frequency on every window, so the copy cannot drift from the toolbox unnoticed. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

29. Two more limits apply besides the build spec's. The peak frequency of the C detector equals the toolbox's on every window that is not near a peak tie, because the peak is a fixed step of 0.25 Hz and the build spec's rule allows a different step only near a tie. The low-frequency sum has no limit, because the build spec gives none, and the reports state its largest relative difference. The arm at rest answer already checks it under item 9. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

30. The saved windows are made by tests/detector/make_windows.py, which runs in the reference venv with fixed seeds. It writes tests/detector/windows.csv with one row per reading and tests/detector/answers.csv with one row per window. Each reading is a 32-bit float, and the toolbox runs on the same values as 64-bit floats, so both sides see the same input. There are 322 windows in the groups below. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.
    - 200 windows come from the five kinds in reference/compare.py, which are rest, tremor, small tremor, walk, and walk with tremor, with 40 of each and seed 1.
    - 40 windows sit near the probability cut-off. In 10 of them the toolbox's probability lies between 0.000001 and 0.00005 from the cut-off. In 15 it lies between 0.0002 and 0.001 above the cut-off, and in 15 it lies between 0.0002 and 0.001 below. The peak lies in 3 to 7 Hz and the arm is at rest, so the probability decides the tremor answer.
    - 40 windows sit near the low-frequency sum of 50. In 10 of them the sum lies between 0.0001 and 0.0025 from 50. In 15 it lies between 0.01 and 0.05 above 50, and in 15 it lies between 0.01 and 0.05 below. The model says yes and the peak lies in 3 to 7 Hz, so the arm at rest answer decides the tremor answer.
    - 20 windows have two peaks of almost equal height, one inside 3 to 7 Hz and one outside. In 10 of them the two largest steps differ by between 0.0001 percent and 0.005 percent, and in 10 they differ by between 0.02 and 0.1 percent. The model says yes and the arm is at rest.
    - 20 windows test the ends of the peak band. Five each have their peak at 3.0 Hz, 7.0 Hz, and 7.25 Hz with the model saying yes and the arm at rest, and five have their peak at 2.75 Hz with the model saying yes.
    - One window is all zeros, and one is a 5 Hz shake of 1500 degrees per second clipped at ±1024, as in the plan's Measured so far section.

31. answers.csv holds the window number, the group name, the toolbox's mfcc_1 to mfcc_12, pred_tremor_proba, below_tremor_power, freq_peak, pred_arm_at_rest, pred_tremor_checked, and the peak gap from item 27. Every number is written with the shortest text that gives back the same 64-bit value. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

32. Replay runs as `build/core/replay --pads FILE`. It reads the three gyroscope columns, multiplies them by 180 / 3.141592653589793 in 64-bit floats as numpy's degrees function does, rounds them to 32-bit floats, and cuts the first 50 rows. It prints a CSV header and then one row for each window n that fits, where window n holds rows 100n to 100n + 399 after the cut, as in the plan's Windows section. The columns are window, mfcc_1 to mfcc_12, pred_tremor_proba, below_tremor_power, freq_peak, pred_arm_at_rest, and pred_tremor_checked, which are the toolbox's names. The 32-bit values print with `%.9g`, the 64-bit values with `%.17g`, and the answers as 0 or 1. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

33. The toolbox cuts PADS windows every 4 seconds, so replay window 4k is the toolbox's window k. The PADS match compares only the replay windows whose number divides by 4, which are the same windows the plan's Windows section uses for the share. Window 0 is included, because PADS needs no conversion and the plan leaves window 0 out only because of the converter. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

34. The PADS match is tests/pads/pads_match.py, and it runs in the reference venv. pads_windows.csv does not hold the 12 numbers, so the script runs the toolbox again on each PADS file in the way reference/pads_counts.py does and keeps the 12 numbers. It checks that this run gives the same probability, low-frequency sum, peak, and answers as the committed pads_windows.csv on every window, and it stops with an error if not. It then applies the rule in items 9, 27, and 29 to every window and compares the C counts with the committed pads_counts.csv. It writes tests/pads/pads_match.md, which is committed, and it exits with code 0 only when every check passes. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

35. The tests for the two cases in item 17 load tools/gen_tables.py as a module, set its EXPECTED_SHA256 to the hash of the changed model file, and call main(). This leaves tools/gen_tables.py unchanged. A third case covers a logistic regression with three rows of weights, so both parts of the classifier check have a test. A logistic regression with two classes keeps one row, so the case uses three classes. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

36. specs/tech-stack.md records the KISS FFT commit, the Unity version, the 64-bit scoring step, the CMake and CTest commands, the replay command, and the PADS match command. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.
