# Feature 8 requirements: Pipeline and state tasks

## From the project documents

1. The pipeline task runs the converter and the detector, and it sends each answer to the state task. This comes from the plan's Firmware design section and Build order step 13.
2. Window n of a stretch holds the 100 Hz samples 100n to 100n + 399. The detector runs on window n as soon as sample 100n + 399 exists, so the runs follow the readings and never a timer. This comes from the plan's Windows section.
3. The face uses every window, so it gets a new answer every second. This comes from the Windows section.
4. The session share uses only the windows whose number divides by 4, and it leaves out window 0 of each stretch, which is warming up. This comes from the Windows section.
5. Every answer carries one result code from the single list in core/window.h. Only tremor, no tremor, and arm moving count toward the share. This comes from the Firmware design section.
6. The firmware measures how long each detector run takes on the chip. The chip has no hardware for doubles, so the measured time includes the 64-bit scoring step in software. This comes from Build order step 13 and the roadmap entry for feature 8.
7. The saved windows in tests/detector/ run on the chip, and the chip's numbers are checked with the same rule as tests/detector/test_detector.c. The 12 numbers and the probability agree with the toolbox within 0.0001, and the answers agree except near a cut-off, as Build order step 5 says. This comes from the roadmap entry for feature 8.
8. The pipeline task is the only task that calls the detector, because the detector's work buffers are static. It calls det_init() once before the first window. This comes from specs/tech-stack.md and the roadmap entry for feature 8.
9. The pipeline task owns a conv_t. It calls conv_start() at each new stretch and conv_set_rate() when the time rule gives the stretch its rate. When conv_push() returns false, the stretch must end, and this feature decides how the pipeline task tells the sensor task. This comes from the roadmap entry for feature 8 and requirement 26 of feature 5.
10. The pipeline task owns a win_t. It calls win_start() at each new stretch and gives each answer its result code with res_from_answer(). This comes from the roadmap entry for feature 8.
11. The pipeline task takes sensor_msg_t messages from firmware/main/tasks.h, and only the first message of a burst carries the time rule's flags. This comes from the roadmap entry for feature 8 and requirement 28 of feature 7.
12. The state task owns the current state. It holds the face state, the session share, the dose schedule, and the doses taken, and its rules live in the shared C library with unit tests on the laptop. This comes from the Firmware design section and Build order step 14.
13. The state task passes every answer's code unchanged to share_add() and face_answer(), and it calls dose_tick() at least once a second. The two-in-a-row rule changes only what the face shows. This comes from the roadmap entry for feature 8 and the Response time section.
14. The state task calls face_gap() at each new stretch after a gap, so the face shows Waiting while the watch warms up. The first stretch after power-on or a new session needs no call. This comes from the roadmap entry for feature 8 and requirement 28 of feature 6.
15. Waiting shows while the watch warms up after a start or a gap, or when the sensor has failed. This feature decides when an answer carries the sensor fault code and how a failed sensor reaches the face. This comes from the Watch face section, under The state circle, and the roadmap entry for feature 8.
16. Each part of the watch has one owning task, and the tasks talk through queues. Only the screen task uses LVGL, it only draws what the state task gives it, and detector runs must never hold up the screen. This comes from the Firmware design section.
17. Answers and doses stay in memory for the session, and the watch writes no results to flash. A restart starts a new session. This comes from the Firmware design section.
18. core/ includes no ESP-IDF headers, allocates no memory at run time, and builds with -ffp-contract=off on the laptop and the watch. This comes from the plan's Shared C library section and specs/tech-stack.md.
19. Nothing in reference/ changes, nobody retrains the detector or changes its stored numbers, and no code or test assumes a rate of 112.1 readings a second. This comes from CLAUDE.md and the roadmap entry for feature 5.

## Not covered by the project documents

Each item below is a choice that the build spec and the existing code leave open.

20. The pipeline task's rules live in core/pipeline.h and core/pipeline.c with the prefix pipe_, so the laptop can test them. A pipe_t holds the conv_t, the win_t, the current stretch as an rt_stretch_t, and the sync state. The caller owns it, and the file has no static data that changes. pipe_part() takes the fields of one sensor message before its readings, pipe_push() takes one reading, and pipe_window() gives the next complete window with its number and the time of its last sample from rt_sample_time_us(). The pipeline task runs the detector itself, so the timer that measures each run stays out of core/. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

21. pipe_part() follows the stretches with these rules. A part with RT_NEW_STRETCH starts a new stretch with conv_start() and win_start(), takes the part's stamp as t0, and returns PIPE_STRETCH. A part with a stretch number that differs from the current one and no RT_NEW_STRETCH has lost its start. A part whose first reading number does not follow the part before has lost readings. In both cases pipe_part() returns PIPE_END and PIPE_DROP, and every later part of that stretch returns PIPE_DROP until the next RT_NEW_STRETCH. pipe_push() returns PIPE_END when conv_push() returns false, and the stretch then drops in the same way. Each stretch asks to end at most once. The rate comes from the part's rate_uhz field the first time it is not 0, so a lost first part does not lose the rate. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

22. The pipeline task tells the sensor task to end a stretch through a new queue of one stretch number, which it writes with xQueueOverwrite(). The sensor task reads the queue with no wait before each good burst. When the number is the current stretch, it passes that burst to rt_burst() with the overflow flag set, so the time rule ends the stretch as it does after a lost burst. The STRETCH line gives kind=1 and reason=pipeline, because the pipeline lost readings, and SENSOR_MINUTE gains the count pipeline=<n> at its end. The pipeline task writes `END_REQUEST stretch=<n> reason=<break|missed_start|ring_full>`. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

23. A sensor fault answer comes when no sensor message has arrived for 2 seconds, and then once a second until a message arrives. The sensor task already waits 1 second before it counts a stall and resets the buffer, so 2 seconds gives it one try first. Bursts arrive about every 0.1 seconds. The face shows Waiting at the second fault answer, which is about 3 seconds after the sensor stopped, because two answers in a row must agree. A fault answer has no window number and no detector numbers, so it goes to face_answer() and never to share_add(). The fault clock starts when the pipeline task starts, so a sensor that fails its setup also reaches the face. When readings come back, the sensor task's overflow flag ends the stretch, and face_gap() keeps Waiting until two answers in the new stretch agree. Feature 9 decides how the W line writes a fault answer. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

24. The state task's rules live in core/session.h and core/session.c with the prefix sess_. A sess_t holds a share_t, a face_t, a dose_t, and counts of answers by code, gaps, and face changes. sess_init() runs dose_init(), share_start(), and face_init(). sess_new_session() runs share_start(), face_init(), and dose_new_session(), and feature 9's command calls it. sess_stretch() calls face_gap() for every stretch number above 0, since every such stretch follows a gap. sess_answer() passes the code unchanged to face_answer(), and to share_add() when the answer has a window. sess_tick() calls dose_tick() and sets the face's dose due flag from its result. Each function returns SESS_FACE_CHANGED when the shown state changes, sess_answer() returns SESS_COUNTED when the share counts the answer, and sess_tick() returns SESS_TONE when a dose becomes due. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

25. A detector answer's time for share_add() and face_answer() is the time of the window's last 100 Hz sample, which is t0 + 10000 × (100n + 399) microseconds. The same time on the laptop gives the same blocks and the same last tremor time, so feature 10 can check them. A fault answer's time is the timer value when it became due. The share's session start is the timer value when the state task starts. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

26. In this feature the dose clock and the schedule stay unset, so no dose becomes due on the watch. Feature 9 adds the commands that set them and the settings store that keeps the schedule. The laptop tests of sess_tick() cover the due path. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

27. The pipeline task sends the state task a message for each new stretch and each answer through a new queue of 8 messages, and it never waits on it. A dropped message counts as an answer drop. An answer message holds the stretch number, whether it has a window, the window number, the code, the probability, the low-frequency sum, the peak, the window's time, the run time, the timer value at the end of the run, and the delay from the stamp of the burst that completed the window. The state task writes `ANSWER`, `GAP`, and `FACE` lines in the order it handles them, so their order in the log is the order of the rules. These lines and the new minute fields exist for this feature's checks, and feature 9 decides the recording lines. Feature 7's lines keep their fields, and new fields go at the end, so tests/firmware/table_run.py still judges the log. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

28. The pipeline task times each det_run() call with esp_timer_get_time() in microseconds. The firmware keeps ESP-IDF's default -Og optimisation, which feature 7 used, and the run time is measured at that level. The run time has no pass limit, because the build spec gives none. The pass checks instead show that the pipeline keeps up, because no message, answer, or reading is dropped and an answer comes about once a second. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

29. The saved windows run on the chip in a separate ESP-IDF project, firmware/detector_check/, because 322 windows take 1,545,600 bytes and do not belong in the watch firmware. tests/firmware/windows_bin.py turns tests/detector/windows.csv into little-endian 32-bit floats at build time, and the project embeds the file. The script reads each value with Python's float() and casts it to a 32-bit float. This gives the value that strtof() gives in test_detector.c unless the 64-bit value lies within a step or two of the halfway point between two 32-bit floats. A pytest finds every such value with numpy and checks it with exact fractions. The project uses the core component with its own flags, the CPU and flash settings of firmware/sdkconfig.defaults, and a partition table with a 3 MB app. It checks the CRC-32 of the data, then runs every window twice in a task on core 1 at the pipeline task's priority, and writes each result. tests/firmware/chip_windows.py judges the output on the laptop with the rule of test_detector.c and writes tests/firmware/chip_windows_log.txt and tests/firmware/chip_windows_report.md. The validate stage commits both files. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

30. The holding screen gains a third label with the name of the shown face state from face_name(). The state task sends the screen task a message at each face change and once a second. SCREEN_MINUTE gains `face=<n> face_changes=<n>` at its end. Feature 11 replaces the holding screen with the face. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

31. tests/firmware/pipeline_run.py runs the watch on a table for 30 minutes, as table_run.py does. It judges the log with table_run.py's 13 pass checks and with this feature's pass checks, and it writes tests/firmware/pipeline_log.txt and tests/firmware/pipeline_report.md. The validate stage commits both files. The watch lies still, so the run cannot show a real tremor answer. Feature 12 tests real shakes on the wrist, and manual check 11 lets the user try one sooner. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

32. `make check` stays as feature 7 wrote it. It now runs 11 CTest tests, and it does not build firmware/detector_check/, because the chip check needs the watch. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

33. specs/tech-stack.md records core/pipeline.h, core/session.h, the end request queue, the sensor fault rule, firmware/detector_check/, and the two new watch commands. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.
