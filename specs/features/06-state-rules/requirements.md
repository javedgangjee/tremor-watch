# Feature 6 requirements: Windows, share, and state rules

## From the project documents

1. Window n of a stretch holds the 100 Hz readings numbered 100n to 100n + 399. The detector runs on window n as soon as reading 100n + 399 exists, so the runs follow the readings and never a timer. This comes from the plan's Windows section.
2. The face uses every window, so it gets a new answer every second. This comes from the Windows section.
3. The session share uses only the windows whose number divides by 4. These are the windows the toolbox cuts, so the share matches the toolbox's. This comes from the Windows section.
4. Window 0 of each stretch is warming up, and it is left out of the share. This comes from the Windows section.
5. Every answer carries one result code from a single list in the shared library. The codes are tremor, no tremor, arm moving, warming up, and sensor fault. Only tremor, no tremor, and arm moving count toward the share, and there is no idle code. This comes from the Firmware design section.
6. The share is the share of still time with tremor, and still time is the time that the detector's arm at rest answer marks. This comes from the plan's The detector section. The toolbox's aggregate_tremor() in ParaDigMa 1.1.2 divides the number of tremor windows by the number of windows at rest and multiplies by 100. The toolbox is the reference, as CLAUDE.md says.
7. The face changes only when two answers in a row agree, and a single odd answer never shows. The rule changes only what the face shows, and every answer still goes into the share and the recording unchanged. This comes from the Response time section.
8. In the plan's simulated demo with the rule, the face showed Tremor about 2.5 to 3.5 seconds after the shake started and at most about 5 seconds at 4 shakes a second. It held Tremor for the whole of a 20 second shake, and it went back to No tremor about 4.5 to 5.5 seconds after the shake stopped. A shake slower than 3 times a second shows Arm moving, and one faster than 7 times a second shows No tremor. This comes from the Response time section. With the forearm lifted, the face showed Arm moving for most of the shake. This comes from the Measured so far section.
9. The face states are Tremor, No tremor, Arm moving, Waiting, and Dose due. Waiting shows while the watch warms up after a start or a gap, or when the sensor has failed. Dose due takes over the circle until the due state ends, and then the detector state returns. This comes from the Watch face section, under The state circle.
10. The state task holds the face state, the session share, the dose schedule, and the doses taken. Its rules live in the shared C library and have unit tests on the laptop. This comes from the Firmware design section.
11. The dose schedule has one medicine name and up to six local clock times a day. This comes from the Dose schedule section.
12. A dose time becomes due at that clock time unless a dose was logged in the hour before it. This comes from the Dose schedule section.
13. When a dose becomes due, the circle shows Dose due and the tone plays three times. This comes from the Dose schedule section.
14. The due state ends when "Took it" is tapped or fifteen minutes pass, and the watch does not remind again. This comes from the Dose schedule section.
15. A dose logged by mistake stays in the recording, and no action has an undo. This comes from the Dose schedule section and the Watch face section, under Behaviour.
16. Until the clock is set, the dose schedule stays off. This comes from the USB recording section.
17. Answers and doses stay in memory for the session. A restart starts a new session, and a laptop command can also start one. This comes from the Firmware design and USB recording sections.
18. After a dose is logged, the button area ignores taps for three seconds, so a second tap cannot log a second dose. This comes from the Watch face section, under Who wears it.
19. The Home screen shows "Last tremor 14:32" under the circle. The Medication screen shows the last dose and the next one due. The Session screen shows the share and up to twelve blocks, one for each 10 minutes of the session, and a block with under two minutes of still time is drawn hollow. This comes from the Watch face section, under Screens. The state task holds these numbers, so their rules belong in this feature, and feature 11 draws them.
20. The new code includes no ESP-IDF headers, allocates no memory at run time, gives every buffer a fixed size, builds with -ffp-contract=off, and builds as part of the plain C library on the laptop. This comes from the plan's Shared C library section and specs/tech-stack.md.
21. The window rule, the session share, and the face state rules have unit tests for every state change, the two-in-a-row rule, and the dose due timing. This comes from Build order step 9 and the roadmap entry for feature 6. The C unit tests use Unity and run on the laptop through CTest, as specs/tech-stack.md says.
22. Nothing in reference/ changes, and nobody retrains the detector or changes its stored numbers. No new code or test assumes a rate of 112.1 readings a second. This comes from CLAUDE.md and the roadmap entry for feature 5.

## Not covered by the project documents

Each item below is a choice that the build spec and the existing code leave open.

23. The rules live in four pairs of files. core/window.h and core/window.c hold the result codes with the prefix res_ and the window rule with the prefix win_. core/share.h and core/share.c hold the session share with the prefix share_. core/face.h and core/face.c hold the face state with the prefix face_. core/dose.h and core/dose.c hold the dose schedule with the prefix dose_. Each keeps its state in a struct that the caller owns, and no file has static data that changes. On the watch the pipeline task owns the window rule, and the state task owns the share, the face, and the doses, as the Firmware design section splits the work. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

24. The result codes have fixed numbers in the build spec's order. Tremor is 0, no tremor is 1, arm moving is 2, warming up is 3, and sensor fault is 4. The W line of feature 9 writes these numbers. `res_from_answer(window, result)` gives warming up for window 0, and for any other window it gives tremor when the detector says tremor, no tremor when the arm is at rest, and arm moving otherwise. These are the labels in reference/demo_test.py. The detector never gives sensor fault, and feature 7 or 8 decides when the firmware sends it. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

25. The window rule takes the converter's blocks in order. Block b starts at sample 100b, and window n is complete when block n + 3 arrives. `win_push_block()` copies the complete window into the caller's 400 by 3 array in sample order. It refuses a block whose first sample is not the next one, and the refusal changes nothing. `win_start()` runs at each new stretch, so the next block must start at sample 0. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

26. `share_add()` counts an answer when its window number divides by 4, the number is not 0, and its code is tremor, no tremor, or arm moving. The share is `(double)tremor / (double)(tremor + no_tremor) * 100.0`, with the division first, as aggregate_tremor() does it. There is no share while no still window has been counted, where the toolbox raises a warning. An arm moving window is counted, but it is in neither part of the share, as in the toolbox. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

27. Block k of the Session screen holds the counted windows whose time lies from k × 600 seconds up to but not including (k + 1) × 600 seconds after the session start. The time of a window is the time of its last 100 Hz sample, which rt_sample_time_us() in core/reading_time.h gives. A window with a time before the session start goes in block 0. Each still window adds 4 seconds of still time, because counted windows lie 4 seconds apart. A block is hollow when its still time is under 120 seconds, which is fewer than 30 still windows. The share keeps the latest 12 blocks. A window in a later block adds the blocks up to it, and the oldest blocks drop when there are more than 12. Blocks with no counted window stay empty and hollow. Each block also gives its own share by the formula in item 26. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

28. The face states have fixed numbers. Tremor is 0, No tremor is 1, Arm moving is 2, Waiting is 3, and Dose due is 4. The F line of feature 9 writes these numbers. Tremor, no tremor, and arm moving answers map to the face state of the same name, and warming up and sensor fault answers both map to Waiting. Two answers agree when they map to the same face state. The face starts in Waiting with no answer before. The detector state takes the state of an answer when the answer before it maps to the same state. A gap is an event apart from the answers. When a new stretch starts after a gap, the state task calls `face_gap()`. It sets the detector state to Waiting at once and clears the answer before, so an answer from the old stretch never pairs with an answer from the new one. It keeps the last tremor time and the dose due flag. After the gap, the face leaves Waiting only when two answers in a row in the new stretch agree. While a dose is due, the face still shows Dose due, and the detector state underneath becomes Waiting. The first stretch after power-on or a new session needs no call, because `face_init()` already sets Waiting with no answer before, and a call there changes nothing. The face shows Dose due while a dose is due and the detector state otherwise. `face_answer()`, `face_gap()`, and `face_set_dose_due()` return true when the shown state changes, so the state task knows when to write an F line. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026. The user chose the gap rule on 23 October 2026.

29. The last tremor time is the time of the latest tremor answer after which the detector state is Tremor. A single tremor answer that does not show sets no time, because a single odd answer never shows. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

30. The dose rules count time in the watch's 64-bit microsecond timer. The local clock is that timer plus an offset, which `dose_set_clock()` sets. Feature 9 works the offset out from the UTC time and the local offset in the clock command. A schedule holds a name of up to 20 bytes and 0 to 6 different times, each a minute of the day from 0 to 1439. `dose_set_schedule()` keeps the times in rising order and refuses a schedule that breaks these limits, and a refused schedule leaves the old one in place. A schedule with no times is off. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

31. The state task calls `dose_tick()` at least once a second. At each tick, the latest scheduled time D that meets three tests becomes due. The tests are that D lies after the last tick and not after now, that now is less than D plus 15 minutes, and that no dose was logged from D minus 1 hour to D, with both ends included. A dose time that becomes due while another is due takes its place, and the tick returns DOSE_BECAME_DUE, so the tone plays. A due dose ends at the first tick at or after D plus 15 minutes, and that tick returns DOSE_DUE_ENDED. Nothing becomes due while the clock is not set. Setting the clock, setting the schedule, and starting a session each count as a tick that makes nothing due, so a dose time that passed before them never becomes due. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026. A due dose also ends at the first tick after a new schedule that no longer holds its time, and that tick returns DOSE_DUE_ENDED, so the face and the Medication screen drop Dose due within a second. This holds for an empty schedule too. A due dose whose time the new schedule still holds stays due, and it ends at D plus 15 minutes as before. The user asked for this fix on 27 October 2026.

32. `dose_took_it()` refuses a tap that comes less than 3 seconds after the last accepted dose. This is the three second lock of item 18 in the shared library, and feature 11 uses the refusal. An accepted tap logs a dose with its time and the scheduled time it answers, and it ends a due dose. The answered time is the due dose's time when a dose is due. Otherwise it is the scheduled time nearest to the tap, before or after, with a tie going to the earlier one. It is -1 when the clock is not set or the schedule is off. The D line of feature 9 writes the answered time. The dose rules keep the latest 8 doses and a count of every dose in the session. With a tick every second and the three second lock, the hour rule never needs a dose older than the latest 8. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026. Before it picks the answered time, an accepted tap applies the due rule of item 31 at the tap's time, as a tick would. So a tap in the second after a dose time D, before that second's tick, finds D due and answers it, and D does not become due after the tap. This tick inside the tap returns no flags, so no tone plays for D. When the state task takes a tap after a tick that came later than the tap, the tap skips this step, so the last tick never moves back. The user asked for this fix on 27 October 2026.

33. `dose_next()` gives the dose time that the Medication screen shows. It is the due dose's time while a dose is due. Otherwise it is the first scheduled time after now that no logged dose covers by the hour rule of item 12. It gives nothing when the clock is not set or the schedule is off. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

34. A new session restarts the share with `share_start()`, the face with `face_init()`, and the doses with `dose_new_session()`. A restart does the same. `dose_new_session()` drops the doses taken and any due dose, and it keeps the schedule and the clock offset. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

35. The response time numbers of item 8 become a C test, tests/response/test_response.c. It builds each session in C with the signal of make_session() in reference/demo_test.py and its own seeded random numbers, at the board's rate of 114330200 millionths of a reading per second. It runs the readings through the C converter, the window rule, the C detector, and the face rule, and it checks the limits in validation.md. The limits allow one more answer, which is one second, past the plan's words "about 5 seconds" and "about 4½ to 5½ seconds", because the C random numbers differ from numpy's. A planning model on 22 October 2026 ran the same sessions in Python with plain_detector.py and the rule, and validation.md gives its numbers. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

36. tests/share/test_share_toolbox.py checks in the reference venv that aggregate_tremor() gives the same share as the C test's cases for the same counts of tremor, no tremor, and arm moving windows. It gives every tremor window a different tremor power, because the toolbox's power summary fails on equal values. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.

37. specs/tech-stack.md records the four new pairs of files and what each holds. The agent decided this on 22 October 2026, and the user accepted it on 27 October 2026.
