# Feature 7 requirements: Commit checks, firmware base, and sensor task

## From the project documents

1. One make command runs the checks for every commit. They build core/ on the laptop, run the unit tests, the saved windows, and the saved converter cases, check the model file's hash against the committed tables, and build the firmware. None of them needs the toolbox. This comes from Build order step 10 and specs/tech-stack.md, under Tests and checks.
2. The hash check compares the model file's SHA-256 hash with DET_MODEL_SHA256 in core/detector_tables.h. This comes from the roadmap entry for feature 7 and the plan's Shared C library section.
3. The full PADS match needs the toolbox, so it stays out of the commit checks and runs before each release. This comes from Build order step 6 and specs/tech-stack.md.
4. core/ builds as an ESP-IDF component for the watch and as a plain C library on the laptop. The component builds with -ffp-contract=off and with the KISS_FFT_MALLOC and KISS_FFT_FREE options from core/CMakeLists.txt, so KISS FFT never touches the heap on the watch. core/ includes no ESP-IDF headers and allocates no memory at run time. This comes from the plan's Shared C library section, the roadmap entry for feature 7, and specs/tech-stack.md.
5. The firmware starts from Waveshare's ESP-IDF example. It keeps the display, touch, IMU, and power drivers and removes the demo apps. This comes from Build order step 11.
6. The firmware uses ESP-IDF v6.1, the board support package waveshare/esp32_s3_touch_amoled_2_06 at version 2.0.0, the QMI8658 driver waveshare/qmi8658 at version 2.0.2, and LVGL 9.5.0. This comes from specs/tech-stack.md.
7. The firmware has five tasks, which are sensor, pipeline, state, screen, and USB. Each part of the watch has one owning task, and the tasks talk through queues. Only the screen task uses LVGL, and detector runs must never hold up the screen. This comes from the plan's Firmware design section and specs/tech-stack.md.
8. firmware/ holds the ESP-IDF project for the watch. This comes from the plan's Repo layout section.
9. The sensor runs rate code 0x06 with the gyroscope and the accelerometer both on, and the gyroscope range is ±1024 degrees per second. This comes from the plan's Sensor and converter section and specs/tech-stack.md.
10. The sensor collects about 11 readings in its buffer, which is about 100 milliseconds, and raises an interrupt. The firmware stamps the burst with the 64-bit microsecond timer inside that interrupt. This comes from the plan's Sensor and converter section.
11. The sensor task reads the IMU, stamps the bursts, gives each reading its time, and starts a new stretch after a gap. It calls rt_burst() from core/reading_time.h once for each burst, with the first reading's number counted from power-on, the number of readings, the stamp taken inside the interrupt, and the overflow flag. This comes from the plan's Firmware design section and the roadmap entry for feature 7.
12. The sensor task turns the raw gyroscope counts into degrees per second. This comes from the roadmap entry for feature 7 and requirement 27 of feature 5.
13. The touch, clock, and power chips share the IMU's I2C bus, and ESP-IDF's I2C driver handles the sharing. This comes from the plan's Firmware design section.
14. The screen stays on for the whole session. This comes from the plan's Watch face section and specs/tech-stack.md.
15. The watch writes nothing to flash in this feature. Only answers and doses stay in memory, and only the dose schedule and the tone setting go in the settings store, which later features add. This comes from the plan's Firmware design section.
16. This feature counts how often stretches end and how long they last with the watch on a table only. It counts two kinds of stretch end apart. The first kind loses readings, because the sensor's buffer overflowed or a reading number was skipped. The second kind loses no readings and comes from the time rule alone. The count is a measurement for the user's later decision about drift, so it has no pass limit on how often the second kind ends a stretch. This comes from the roadmap entry for feature 7.
17. No code or test assumes a rate of 112.1 readings a second, and each stretch takes its rate from the reading times. This comes from the roadmap entry for feature 5.
18. Nothing in reference/ changes, and nobody retrains the detector or changes its stored numbers. This comes from CLAUDE.md.

## Not covered by the project documents

Each item below is a choice that the build spec and the existing code leave open.

19. A Makefile at the repo root holds the commit checks. `make check` runs the targets `laptop`, `hash`, and `firmware` in that order and stops at the first failure. `make laptop` runs `cmake -S . -B build && cmake --build build && ctest --test-dir build --output-on-failure`, so test_detector runs the saved windows and test_converter runs the saved converter cases. `make hash` compares the hash of the file `MODEL` with DET_MODEL_SHA256 in the file `TABLES`, and both names can be set on the command line for tests. `make firmware` builds firmware/ with `idf.py -C firmware build`. It loads ESP-IDF with `. $(IDF_ACTIVATE)` when idf.py is not on the path, and IDF_ACTIVATE defaults to `$(HOME)/.espressif/tools/activate_idf_v6.1.sh`. On this laptop `. ~/.espressif/v6.1/esp-idf/export.sh` fails unless IDF_TOOLS_PATH is `~/.espressif/tools`, and the activate script sets it. The Makefile uses no Python and nothing from reference/.venv. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

20. The model file lives in the toolbox's install, so the hash check needs a copy that comes without the toolbox. tests/model/tremor_detection_clf_package.pkl is an unchanged copy of the ParaDigMa 1.1.2 model file, and tests/model/LICENSE is an unchanged copy of ParaDigMa's Apache 2.0 licence from the installed package. `make hash` hashes this copy with `shasum -a 256`. tests/model/test_model_copy.py checks in the reference venv that the copy is the same byte for byte as the toolbox's file. Nothing ever loads the copy as a model. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

21. Nothing runs `make check` by itself. The project adds no git hook and no CI, because a firmware build on each commit is slow and a hook lives outside the repo. The implement and validate stages run `make check`, and the user runs it before a commit. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

22. core/CMakeLists.txt gets an ESP-IDF branch at the top. When ESP_PLATFORM is set, it registers every library source with idf_component_register() and returns before the laptop part, so the source list stays in one file. The component is named core, after its folder. firmware/CMakeLists.txt adds the folder with EXTRA_COMPONENT_DIRS. The project's own C files in the component build with -Wall -Wextra -Werror -pedantic -ffp-contract=off, and the KISS FFT files build with -ffp-contract=off only, as on the laptop. Both get the two KISS FFT options. replay stays a laptop program. A planning run on 23 October 2026 compiled every file in core/ with xtensa-esp32s3-elf-gcc from ESP-IDF v6.1 and these flags, and it gave no warning and no heap symbol. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

23. The ESP-IDF project sits in firmware/ itself. Its build files start from examples/esp-idf/02_lvgl_demo_v9 in Waveshare's repo at commit 30f3b23, which feature 1 built and flashed with ESP-IDF v6.1. The demo sources, the demo settings, and the `-Wno-format` option are left out. The partition table is the single large app table that firmware/bringup/ uses, because nothing needs Waveshare's storage partition. firmware/sdkconfig and firmware/dependencies.lock are committed, as feature 1 did for firmware/bringup/. firmware/bringup/ stays unchanged as feature 1's record, because firmware/bringup/rate_log.txt holds the measured rate. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

24. The power driver is XPowersLib, copied unchanged from examples/esp-idf/01_AXP2101/components/XPowersLib/ in Waveshare's repo into firmware/components/XPowersLib/. Its source files carry their own MIT licence text. firmware/main/power.h and firmware/main/power.cpp give C functions that reach the AXP2101 at address 0x34 on the board support package's I2C bus through XPowersLib's register callbacks, as Waveshare's factory example does. They do not change the charge settings. In this feature the firmware reads the power chip once at start and writes whether USB power is in, whether a battery is in, the battery voltage, and the battery percentage. A planning run on 23 October 2026 compiled the copy with the ESP-IDF v6.1 compiler. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

25. The QMI8658 raises its buffer interrupt on its INT1 pin, which the board's schematic wires to GPIO21. The schematic is hardware/schematic/ESP32-S3-Touch-AMOLED-2.06-Schematic-V1.0.pdf in Waveshare's repo, and it does not wire INT2 to the ESP32-S3. The sensor task sets the buffer to FIFO mode with room for 128 readings and a watermark of 11 readings, routes the watermark interrupt to INT1, and turns INT1 on. The interrupt handler fires on the rising edge, takes esp_timer_get_time(), and sends the stamp to the sensor task. The sensor task reads the buffer in the order that SensorLib's readFromFifo() uses in Waveshare's Arduino libraries. Each reading is 12 bytes, which are the accelerometer x, y, and z and then the gyroscope x, y, and z, each a little-endian 16-bit count. The accelerometer range stays ±8 g, as in feature 1. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

26. A reading's number is a 64-bit count of the readings that the sensor task has taken from the buffer since power-on, starting at 0. A burst holds the readings of one buffer read. A burst cannot be trusted when the buffer status shows an overflow or a full buffer, when a bus read fails, when no interrupt comes for 1 second, or when INT1 is still high after a read, because the next rising edge would then never come. The sensor task then drops that burst's readings, resets the buffer, and gives no numbers to the dropped readings. It passes the next good burst to rt_burst() with the overflow flag set. So every loss ends a stretch exactly once, and the new stretch's t0 comes from a clean rising edge. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

27. core/imu_units.h and core/imu_units.c hold the gyroscope's unit rule for the watch and for replay in feature 10. They define IMU_GYRO_RANGE_DPS as 1024 and IMU_GYRO_COUNTS_PER_DPS as 32, and `float imu_gyro_dps(int16_t raw)` returns raw / 32 as a 32-bit float. Every count gives an exact float, which matches the converter cases of feature 5, where every reading is a whole number of counts divided by 32. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

28. The sensor task sends the pipeline task one message for each part of a burst. A message holds the burst's rt_burst() flags, the overflow flag, the stretch number and rate after the call, the stamp, the first reading's number, a count, and up to 16 readings with both the raw counts of all six axes and the gyroscope in degrees per second. A burst of more than 16 readings goes in more than one message, and only the first part carries the flags. The sensor task never waits on a full queue. It drops the message and counts the drop. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

29. In this feature only the sensor task and the USB task do their full work. The pipeline task takes every message, checks that the reading numbers follow on, and keeps each minute's sums for the gyroscope and the accelerometer. The state task sends the screen task the uptime once a second. The screen task calls bsp_display_start(), draws a plain holding screen with the words "Tremor log" and the uptime in a font of at least 28 pixels, and writes a line for each tap. The BSP's LVGL port task runs LVGL's timers, and the screen task holds the port's lock for every change. No other task of this project calls LVGL. The USB task is the only task that writes to the serial port. The other tasks send it lines through a queue, never wait on it, and count the lines they drop. Feature 8 writes the pipeline and state tasks, feature 9 writes the recording lines, and feature 11 writes the face. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

30. The sensor task has the highest priority of the five tasks and runs on core 1, as feature 1's rate task did. The USB task has the lowest. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

31. A stretch end is the first kind when the burst that ended it carried the overflow flag or its first reading number did not follow the burst before. The firmware also writes the reason, which is overflow, full, read error, stall, or late. A stretch end is the second kind in every other case. For each end the firmware writes the ended stretch's length from its first to its last stamp, its reading count, and its rate. For an end of the second kind it also writes the stamp minus the old stretch's prediction in microseconds, or no value when the old stretch had no rate yet. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

32. The table run lasts 30 minutes of watch uptime from the start line. tests/firmware/table_run.py runs it with the ESP-IDF Python, which has pyserial 3.5. It resets the watch through the port, saves every line to tests/firmware/table_log.txt, and writes tests/firmware/table_report.md. It can also judge a saved log with `--log-only`. It exits with code 0 only when every pass check in validation.md check 9 holds. The validate stage commits the two files as the measured record, as feature 1 committed rate_log.txt. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

33. The table run requires no stretch end of the first kind, no bus error, and no dropped message, because a watch at rest with no detector running must not lose readings. It also requires every rate from the time rule to lie within 1000 parts per million of 114330200, which is the 20-minute rate that feature 1 measured with the sensor's own counter. This compares the sensor task's numbers and stamps with a separate method. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

34. specs/tech-stack.md records the make command, the firmware layout, the ESP-IDF activate script, XPowersLib, the core component, core/imu_units.h, the model copy, and the table run command. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.
