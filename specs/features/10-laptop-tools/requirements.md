# Feature 10 requirements: Laptop tools

## From the project documents

1. tools/watch_cli.py sets the watch's clock and its dose schedule, starts a session, and saves the recording to a file. It sends the commands of the USB recording section, which also turn the tone on or off. This comes from Build order step 16 and the plan's USB recording section.
2. The clock command carries the time in UTC and the local offset. Until the clock is set, the dose schedule stays off. The clock lives in memory only, so a restart leaves it unset until the laptop sends the clock command again. This comes from the USB recording section and specs/tech-stack.md.
3. tools/compare_session.py runs replay on a recording and reports any window where the watch's answer differs, under the rule in Build order step 5. This comes from Build order step 17.
4. The rule in step 5 says that the 12 numbers and the probability agree within 0.0001. The answers agree on every window, except where the reference's probability sits within 0.0001 of its cut-off, its low-frequency sum sits within 0.01 percent of 50, or its two largest peak steps differ by less than 0.01 percent. This comes from Build order step 5.
5. compare_session.py then runs the toolbox on each stretch with its conversion set to 100, using the reading times from the recording, and it reports how often the watch agrees. Left to its defaults, the toolbox works at the rate it is given, and 2 of 100 windows gave a different answer at 112.1 Hz than at 100 Hz. This comes from Build order step 17 and the plan's Measured so far section.
6. compare_session.py leaves out window 0 of each stretch, because it is warming up and the toolbox treats the start of a recording in its own way. This comes from Build order step 17 and the plan's Windows section.
7. The laptop build includes replay, a command-line program that reads a recording or a PADS file and prints its own answer for every window. The PADS input stays as feature 4 wrote it. This comes from the plan's Shared C library section and the roadmap entry for feature 10.
8. replay gives each reading its time with core/reading_time.c from the T lines, so the laptop gives every reading the same time the watch gave it. Time stays as whole reading counts and 64-bit microsecond stamps, and never as 32-bit seconds. This comes from the plan's Sensor and converter section and the roadmap entry for feature 10.
9. The toolbox gets the reading times of each stretch as `n * 1e6 / rate_uhz` seconds in 64-bit floats, counted from the stretch's t0 and not rounded. This comes from requirement 30 of feature 5 and the roadmap entry for feature 10.
10. Window n of a stretch holds the 100 Hz samples 100n to 100n + 399. The toolbox cuts a window every 4 seconds, so its window k is the watch's window 4k. This comes from the plan's Windows section.
11. The time of a window's answer is the time of its last 100 Hz sample, which is t0 + 10000 × (100n + 399) microseconds. This comes from requirement 25 of feature 8 and the roadmap entry for feature 10.
12. A reader skips every line before the first B line, skips the diagnostic lines, and takes the last S line of each stretch number. The S line of each stretch comes before its first T line. After a drop, the watch writes the B line and the latest S line again. This comes from core/recording_format.md and the roadmap entry for feature 10.
13. When the laptop closes the port, the Mac throws away the bytes it already holds. So a recording that opens the port again can start with part of a line and miss a few lines from before the close. This comes from the roadmap entry for feature 10.
14. pyserial sets DTR before RTS when it opens a port, and the chip resets while RTS is high and DTR is low. A tool that must not reset the watch opens the port as open_port() in tests/firmware/record_run.py does. This comes from the roadmap entry for feature 10.
15. The Mac's C library writes all 17 digits for %.17g, so laptop code that must write the watch's text for the detector numbers uses the functions of core/record.h. This comes from the roadmap entry for feature 10.
16. tests/firmware/record_log.txt.gz holds a full 30-minute recording from the table, and this feature can use it to test replay. This comes from the roadmap entry for feature 10.
17. A session report shows that replay agreed with the watch on every window, and how often the toolbox agreed. Feature 12 makes this report for the demo session with compare_session.py. This comes from the plan's What you deliver section.
18. tools/ holds gen_tables.py, watch_cli.py, and compare_session.py. This comes from the plan's Repo layout section.
19. New Python code follows the user's Python rules, and its tests use pytest in the reference venv. This comes from specs/tech-stack.md.
20. The core/ library includes no ESP-IDF headers, allocates no memory at run time, and builds with -ffp-contract=off. replay builds with the same flags. This comes from the plan's Shared C library section and specs/tech-stack.md.
21. Nothing in reference/ changes, nobody retrains the detector or changes its stored numbers, and no code or test assumes a rate of 112.1 readings a second. This comes from CLAUDE.md and the roadmap entry for feature 5.
22. The build spec's T line holds no overflow flag, so this feature decides how replay finds a stretch that an overflow ended. This comes from the roadmap entry for feature 10, and requirement 23 gives the decision.

## Not covered by the project documents

Each item below is a choice that the build spec and the existing code leave open.

23. replay finds every stretch start from the S lines. When replay reads a T line whose first reading equals the first reading of an S line that came before it in the same boot, it calls rt_burst() with the overflow flag set. Otherwise it calls rt_burst() with the flag clear. The sensor task numbers only the readings it reads, so the T lines alone cannot show an overflow, a lost reading that keeps the numbers in order, or an end request from the pipeline task. The S line is the only mark of such a stretch end. A drift end also gets the flag, and rt_burst() then starts the same stretch at the same burst with the same rate, because the flag only forces the end. The time rule still runs on every burst, so a stretch end that the watch did not make shows as a stretch that has no S line. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

24. replay takes a recording with `replay --recording FILE`, where FILE is a text file of the watch's lines or `-` for the standard input. It skips every line before the first B line, every line that starts with "> ", every diagnostic line, and every other line that is not a record line. A line that starts with a record letter and a comma but breaks its pattern in core/recording_format.md counts as a bad line and is skipped. A B line with a new boot ID starts a new boot, so replay starts the time rule and the pipe again. A B line with the same boot ID is a repeat after a drop and changes nothing. replay keeps each T line until its R lines are in. It passes a burst on only when the burst has exactly its count of R lines, numbered in order, and otherwise it drops the burst and counts it. replay ignores the W, F, D, and A lines. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

25. replay feeds each whole burst to the functions of core/pipeline.h as the pipeline task does, as one part with the time rule's flags, stretch number, and rate. It turns each gyroscope count into degrees per second with imu_gyro_dps(), runs det_run() on each window that pipe_window() gives, and takes the code from res_from_answer(). It makes no sensor fault answer, because those come from the watch's timer. For each window it prints one CSV row with the columns boot, stretch, first, t0_us, rate_uhz, window, time_us, code, mfcc_1 to mfcc_12, pred_tremor_proba, below_tremor_power, freq_peak, pred_arm_at_rest, and pred_tremor_checked. The stretch, first, t0_us, and rate_uhz columns are replay's own stretch from the time rule. The numbers use the formats of the PADS rows. At the end replay writes one line to the standard error with the counts of lines, bad lines, dropped bursts, boots, and stretches. It exits with code 1 when it cannot read the file or the file holds no B line. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

26. `replay --recording FILE --samples OUT` also writes replay's 100 Hz samples to OUT as CSV with the columns boot, stretch, sample, gyroscope_x, gyroscope_y, and gyroscope_z. It writes all 400 samples of window 0 and the last 100 samples of each later window, so each sample appears once. compare_session.py needs them for the peak rule of requirement 28, because the W line holds neither the spectrum nor the two largest peak steps. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

27. compare_session.py checks a stretch only where the recording holds all of its T and R lines from its first reading on. The checked part of a stretch runs from its first reading to the first gap in its T numbers, or to its end. replay's stretch for that part must have the first reading and t0 of the watch's S line of the same boot, and the rate of the last such S line. A stretch that replay starts with no matching S line, a watch stretch that replay does not start, and a rate that differs each fail the run, unless a gap in the T numbers or the start of the recording lies in that stretch or in the stretch before it. Two kinds of window are counted by reason in the report and are not compared. The first lies after a checked part that ended at a gap. The second belongs to the lowest stretch number of its boot in the recording when the recording does not hold that stretch's first reading, because the recording started while the stretch ran. Every other W line with a window must have a replay row. So a W line beyond the end of its stretch fails, and so does a W line of a later stretch that has no S line. A replay row in a checked part must have a W line. The last replay window of each boot is exempt, because the capture or a reset can come before its W line. A run with no checked window fails. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

28. compare_session.py applies the rule of requirement 4 to each checked window from window 1 on, with replay in the reference's place. The W line holds the probability, the low-frequency sum, the peak, and the code, but not the 12 numbers, so the 12 numbers are not compared. The probability must agree within 1e-6. The low-frequency sum must agree within 1e-6 of replay's sum, as a share of that sum. The codes must agree unless replay's probability lies within 0.0001 of the cut-off, replay's low-frequency sum lies within 0.005 of 50, or replay's two largest peak steps from 1 to 25 Hz differ by less than 0.01 percent of the largest. The peaks must agree unless the last of these holds. compare_session.py computes the two largest peak steps from replay's samples with scipy's welch, as tests/detector/make_windows.py does. The three margins are those of tests/pads/pads_match.py. The two limits are much tighter than pads_match.py's 0.0001, because the watch and replay run the same C code and differ only where the chip's maths library and the laptop's differ. On the committed logs of features 9 and 11 the probability differs by at most 2.52e-10, and the low-frequency sum does not differ. On the 322 saved windows of tests/firmware/chip_windows_log.txt, which run from no tremor to tremor, the chip and the laptop build differ by at most 9.9e-8 in the probability and not at all in the sum. So the probability limit is ten times that difference. The sum is a 32-bit float sum, so its limit is relative, and 1e-6 of the sum is about 16 steps of a 32-bit float. The report gives the largest difference in each. compare_session.py compares the numbers as 64-bit doubles read from the text, so no laptop code writes the watch's text. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026. The limits were 0.0001 for the probability and none for the sum until a review found them far looser than the data, and the user asked for this fix on 27 October 2026.

29. compare_session.py runs the toolbox on each checked part of a stretch as one recording. The readings are the gyroscope counts divided by 32 as 64-bit floats, at the times of requirement 9. It sets IMUConfig's resampling_frequency to 100 and calls preprocess_imu_data() with sensor "gyroscope" and watch_side "left", as tests/converter/make_cases.py does. The right side only flips the sign of some axes, which changes no spectrum, so the side cannot change an answer. It then calls extract_tremor_features() and detect_tremor() with the default TremorConfig and the toolbox's own model file, as tests/pads/pads_match.py does. It stops with an error when sample k of the converted stretch does not lie at k × 0.01 seconds within 1e-9 seconds. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

30. The toolbox's code for a window is 0 when pred_tremor_checked is 1, 1 when pred_arm_at_rest is 1 and the window is not tremor, and 2 otherwise, as res_from_answer() gives. compare_session.py compares the toolbox's window k with the watch's W line for window 4k, for every k from 1 on. The report gives the number of these windows, the number where the codes agree, that number as a percentage, the largest difference in the probability, and each window that differs with a note of whether the toolbox's numbers lie near a cut-off under the rule of requirement 28. The toolbox's agreement has no pass limit, because the build spec asks only that it be reported. A planning run on 2026-10-23 gave agreement on all 449 such windows of tests/firmware/record_log.txt.gz, on all 313 of tests/firmware/command_log.txt.gz, and on all 16 before the gap of tests/firmware/drop_log.txt.gz, with a largest probability difference of about 1e-9. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

31. The report also gives the share of still time with tremor over the windows that requirement 30 compares, once from the watch's codes and once from the toolbox's codes, with the rule of core/share.h. This goes beyond the build spec's words. The share is the project's one number, so the report shows whether the watch and the toolbox give the same number for the same windows. The share has no pass limit. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

32. compare_session.py takes `RECORDING`, `--replay` with a default of build/core/replay, and `--report` with a default of the recording's path with its suffixes replaced by `_session.md`. It reads a gzip file when the name ends in `.gz` and a text file otherwise. A gzip file that was cut short, because the recording stopped without closing it, is read up to the cut with its last part line dropped, and the report and the log say so. It drops a leading laptop time and tab from each line, as tests/firmware/record_run.py's read_log() does. It passes the lines to replay on the standard input. It writes the report in Markdown and exits with code 0 only when no check of requirements 27 and 28 fails. The report names the recording, the ParaDigMa version, the boots, every stretch with its watch and replay rates and whether it was checked, the replay results, the toolbox results, and the share. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026. The reading of a cut gzip file came from a review, and the user asked for this fix on 27 October 2026.

33. watch_cli.py has the subcommands `clock`, `schedule NAME [HH:MM ...]`, `schedule --off`, `session`, `tone on`, `tone off`, and `record --out FILE [--minutes M]`, and the option `--port` with a default of /dev/cu.usbmodem101. The reference venv has no pyserial and reference/ must not change, so watch_cli.py runs with the ESP-IDF Python, as the scripts in tests/firmware/ do. It imports serial inside the functions that open the port, so its tests run in the reference venv. It holds its own copy of the port opening of open_port() in tests/firmware/record_run.py, because a tool should not import from tests/. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

34. watch_cli.py takes the UTC time from time.time_ns() // 1000 and the local offset in whole minutes from datetime.now().astimezone().utcoffset(), as tests/firmware/command_run.py does. It turns each HH:MM into the minute of the local day. It refuses a name or a time that the watch would refuse under requirements 30 and 34 of feature 9 before it opens the port, and it exits with code 2. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

35. Each command subcommand opens the port without a reset and reads until one whole line arrives or 2 seconds pass, so the watch's send buffer has room for the answer. It then sends the command with a newline, reads until the A line with the command's number arrives, and gives up after 5 seconds. It logs the A line and exits with code 0 only for result 0. For result 5 it says that the watch was busy and that the command may be sent again. It never sends a command twice. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

36. `record` resets the watch as record_run.py does, so the recording holds the whole boot from its first reading and every stretch can be checked. It writes each line as `<laptop seconds>\t<text>` to a gzip text file, the same form as the logs in tests/firmware/, and it keeps the lines before the B line. After the first B line of each boot it sends the clock command, because the reset left the clock unset, and it writes the command as a `> ` line. A watch that restarts during the recording gets its clock again at its new B line, and a repeated B line of a boot whose clock is set gets no command. A busy answer or no answer sends the command again, up to 3 times. The schedule and the tone live in the settings store, so they survive the reset. It stops after `--minutes` minutes, at Ctrl-C, or at SIGTERM or SIGHUP, which a closed terminal sends, and it closes the file whole in each case. It holds these signals while it writes a line or closes the file, so a signal never cuts the gzip stream. When the port goes, as it does while the cable is out, it waits for the port to come back until the recording stops, says once after 10 seconds that it is waiting, and gives the watch's new B line its clock when the port comes back. It exits with code 1 when the last boot's clock command does not get result 0, and it keeps the file. It refuses to write over a file that exists and exits with code 1 before it opens the port, so a saved recording cannot be lost. The agent decided this on 2026-10-23, and the clock after each restart and the retries on 2026-10-27, and the user accepted it on 27 October 2026. Until a review, only Ctrl-C closed the file whole and a port gone for more than 10 seconds ended the recording with an error, and the user asked for this fix on 27 October 2026.

37. The firmware does not change in this feature, so FIRMWARE_VERSION stays 9. `make check` stays as it is, because compare_session.py needs the toolbox. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026. Later the Makefile gained `make python`, which runs the pytest tests in tests/ with the reference venv or with the interpreter that PYTHON names, and `make full`, which runs `make check` and then `make python`. `make check` still needs no toolbox. The user asked for this fix on 27 October 2026.

38. The tests of replay's recording input are pytest tests in tests/replay/, with a helper there that writes made-up recordings. The tests of the two tools are in tests/tools/. The tests use the three committed logs in tests/firmware/ as real input. The validate stage writes the session report of tests/firmware/record_log.txt.gz to tests/firmware/record_session.md and commits it. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.

39. core/recording_format.md gains a section on saved recordings, which gives the file form of requirement 36 and how replay reads a recording under requirements 23 and 24. specs/tech-stack.md records the two tools, the replay command for a recording, and the commands that run them. The agent decided this on 2026-10-23, and the user accepted it on 27 October 2026.
