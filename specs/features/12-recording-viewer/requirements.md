# Feature 12 requirements: Recording viewer

## From the project documents

1. A small Electron app on the laptop shows a saved recording. This comes from the viewer paragraph in the build spec's USB recording section and the roadmap entry for feature 12.
2. The app opens a file that tools/watch_cli.py saved. That file is gzip text, and each line holds the laptop's time in seconds with three decimals, a tab, and one line from the watch. A line whose text starts with `> ` is a command or a note from the laptop. This comes from the Saved recordings section of core/recording_format.md.
3. The app plots the gyroscope readings against time. A gyroscope count divided by 32 gives degrees per second. This comes from the viewer paragraph, the R line in core/recording_format.md, and IMU_GYRO_COUNTS_PER_DPS in core/imu_units.h.
4. The app marks each window that the watch answered with tremor, which is each W line with result code 0. Window n of a stretch holds the 100 Hz samples 100n to 100n + 399, and sample k lies at t0 + 10000 × k microseconds. This comes from the viewer paragraph, the build spec's Windows section, core/window.h, and rt_sample_time_us() in core/reading_time.h.
5. The app reads saved files only and never opens the watch's port, so tools/watch_cli.py stays the only program that talks to the watch. This comes from the viewer paragraph and the roadmap entry for feature 12.
6. The app reads the lines with the rules that replay and compare_session.py use. It skips every line before the first B line, every `> ` line, every diagnostic line, and every other line that does not start with a record letter and a comma. A line that starts with a record letter and a comma but breaks its pattern counts as a bad line. A B line with the same boot ID is a repeat after a drop, and a new boot ID starts a new boot. The last S line of each stretch number holds. A burst counts only when it holds exactly its count of R lines, numbered in order, and otherwise it is dropped and counted. The last burst of the file is left out without a count when its R lines are in order but too few, because the capture stopped in it. A recording can hold gaps in its T numbers. This comes from core/recording_format.md.
7. Within a stretch, reading n has the time t0 + (n - f0) / r, where t0 is the stamp of the stretch's first burst, f0 is its first reading, and r is the stretch's rate. Time stays as whole reading counts and 64-bit microsecond stamps, and never as 32-bit seconds. This comes from the build spec's section on giving each reading a time and core/reading_time.h.
8. A gzip file that was cut short, as when a recording stops without closing its file, is read up to the cut with its last part line dropped, and the reader says so. This comes from the roadmap entry for feature 10 and the review fixes of 2026-10-27, which made compare_session.py and the judges read such files.
9. The result codes are 0 for tremor, 1 for no tremor, 2 for arm moving, 3 for warming up, and 4 for sensor fault. A sensor fault answer has no window. This comes from core/window.h and core/recording_format.md.
10. The wrist and demo recordings must be easy to look over with the app, and a session lasts one to two hours, which is about 820,000 readings at 114 readings a second. This comes from the roadmap entry for feature 12 and specs/mission.md.
11. Nothing in firmware/, core/, reference/, or tools/ changes, and nobody retrains the detector or changes its stored numbers. This comes from CLAUDE.md.

## Not covered by the project documents

Each item below is a choice that the build spec, specs/, and the existing code leave open.

12. The app lives in viewer/ at the repo root with its own package.json, a committed package-lock.json, and a viewer/.npmrc that sets save-exact. Every version is exact. Electron is 44.7.1, which is the newest Electron release at least two weeks old on 2026-10-27, because 45.0.0 came out on 2026-10-21. The plotting library is uPlot 1.6.32, which has an MIT licence, draws large time series fast, and needs no framework. These are the only two packages, and the app uses no framework, no bundler, and no TypeScript. Node v22.22.1 and npm 11.20.0 from nvm run npm and the unit tests. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

13. `npm --prefix viewer ci` installs the packages once, which needs the network. `npm --prefix viewer start -- [FILE] [--boot ID]` starts the app, and FILE is optional. npm runs the script in viewer/, so the app resolves a relative FILE against the INIT_CWD folder that npm sets, which is the folder the command ran from. The File menu's Open item, Cmd+O, and an Open button show the system's open dialog. A file whose name ends in `.gz` is read as gzip, and any other file as plain text, as compare_session.py does. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

14. The code is split into small modules with one job each. The modules in viewer/src/lib/ read the file, read the line patterns, parse the lines, give each reading its time, and place the windows. They import only Node's built-in modules with the `node:` prefix and each other, never Electron or uPlot. So `node --test` runs their unit tests with no node_modules. viewer/src/main.js owns the window, the menu, the dialog, and the file reading. viewer/src/preload.js passes three calls to the page. The page in viewer/src/renderer/ only draws. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

15. The app reads the record line patterns from the table in core/recording_format.md when it opens a file, with the same row pattern as tools/compare_session.py, so the format has one source. It stops with an error that names the missing letters when the table does not give all of B, S, T, R, W, F, D, and A. The app runs from the repo and is never packaged, so it can always reach the file. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

16. The parser follows requirement 6 and adds these rules from replay and compare_session.py. A T line with a count of 0 or above 256 counts as a bad line. A line whose whole number does not fit a safe JavaScript integer counts as a bad line, and so does an R line whose six counts do not all lie from -32768 to 32767. A W line with a window whose three numbers do not all read as finite numbers counts as a bad line, as compare_session.py skips it. A W line with an empty window is a sensor fault answer, and the app counts it. When two W lines give the same stretch and window in one boot, the last one holds, as for S lines. The F, D, and A lines are checked against their patterns and otherwise ignored. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

17. The app takes each stretch's t0 and rate from the watch's S lines and does not run the time rule itself. A reading belongs to the stretch whose last S line has the largest first reading at or below the reading's number. Its time is t0 + (n - f0) × 1e12 / rate_uhz microseconds as a 64-bit double, the same sum as rt_reading_time_us(), so it differs from the watch's time by less than 1 microsecond. A gap in the T numbers does not change the formula, because the watch's stretch went on, so the readings after a gap keep the watch's times and line up with its windows. When a stretch's last S line gives rate 0, because the capture stopped before the rate was set or the stretch ended before 10 seconds, the app estimates the rate from the stretch's first and last kept bursts. With only one burst it takes the last known rate of the boot, or 114330200 when the boot has none. Such a stretch is marked as estimated in the summary, and its reading times can differ from the watch's by a few milliseconds. The plot breaks its lines at the start of each stretch and at each gap in the kept bursts. A burst that no S line covers is left out and counted. The x axis gives seconds of the watch's timer since its boot. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

18. The W line of window n in stretch s is placed with the last S line of stretch s in the same boot. Its span runs from t0 + n × 1e6 to t0 + (n + 4) × 1e6 microseconds, which covers samples 100n to 100n + 399. Neighbouring spans overlap by 3 seconds, so the plot shades their union. Its answer cell covers the last second of the span, from t0 + (n + 3) × 1e6 microseconds, which is the second the window added. These times are exact, because they need only t0. A W line whose stretch has no S line in its boot is counted as not placed and not drawn. A sensor fault answer has no window, so it is counted and not drawn. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

19. The page shows one boot at a time, with a list to pick the boot when the file holds more than one. It starts with the first boot that has readings, or the boot that `--boot ID` names. The plot draws the gyroscope's x, y, and z axes in degrees per second in the colours #D55E00, #009E73, and #CC79A7 from the Okabe and Ito set, which people with weak colour vision can tell apart. It shades the union of the spans of the tremor windows in the face's Tremor navy #1B2E42 from LOOK_TREMOR in core/look.h at 18 percent opacity. Along the bottom of the plot a lane 16 pixels high draws each placed window's answer cell, with tremor in solid #1B2E42, no tremor in #DDD9D2, arm moving in #A8C9B3, which is a pale tint of LOOK_ARM, and warming up in #EFECE6. A legend names the colours with the names res_name() in core/window.c gives. A summary line gives the file name, whether the file was cut short, the boot ID, the firmware version, the reset cause, each stretch with its rate and whether it is estimated, the number of readings, the number of windows of each code, and the numbers of bad lines, dropped bursts, readings with no stretch, and windows not placed. The accelerometer and the F, D, and A lines are not drawn. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

20. A drag across the plot zooms into that time span, a double click shows the whole boot, and the left and right arrow keys move the view by half its width. The y axis fits the readings in view. uPlot gives the first two, and the arrow keys are a few lines in the page. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

21. The app never crashes on a bad file. The page shows one plain message and clears the plot when the file is missing or cannot be read, when a `.gz` file is not gzip, when the text is longer than 400 MB, which is ten times a two hour session, when the file holds no B line, and when its boots hold no reading. A file that was cut short opens with a note in the summary. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

22. The app follows Electron's security advice. The window has contextIsolation on, nodeIntegration off, sandbox on, and webSecurity on. The preload script uses contextBridge to expose `window.viewer` with three calls only, which are openFile(), onRecording(callback), and reportDrawn(report). The main process reads the file and shows the open dialog, and it answers only messages from its own page. The page has a Content Security Policy of `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; base-uri 'none'; form-action 'none'`. The page loads no remote content, the app denies every new window, navigation, and permission request, and uPlot loads from viewer/node_modules. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

23. `--capture OUT.png` runs the app with no person. It opens FILE, waits until the page has drawn, saves the window to OUT.png with webContents.capturePage(), writes OUT.json, and exits. OUT.json holds the page's report of what it drew, the time to load and to draw in milliseconds, the window's web preferences, whether `require` and `process` exist in the page, and the colour at the centre of each tremor answer cell that is at least 3 pixels wide. The exit code is 0 when the file was drawn, 1 when the file could not be read, in which case the message is in OUT.json and on the standard error and OUT.png shows the message, and 2 for bad arguments or when nothing was drawn within 60 seconds. The agent decided this on 2026-10-27, and the user has not reviewed it yet.

24. A two hour recording of about 823,000 readings opens and draws within 10 seconds on the user's Mac, as OUT.json reports for a made-up recording. The agent decided this on 2026-10-27, and the user has not reviewed it yet.
