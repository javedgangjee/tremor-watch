# Feature 5 requirements: Reading times and converter

## Waiting for the user's review

The validate stage found that requirements 21, 22, and 24 go beyond the build spec's words. The user has not reviewed them yet. The Results section of validation.md explains each one.

## From the project documents

1. Within a stretch, reading n has the time t0 + n / r. Here t0 is the stamp of the stretch's first burst, and r is one fixed rate for the whole stretch. This comes from the plan's Sensor and converter section, under Giving each reading a time.
2. The first stretch after power-on takes its rate from its first 10 seconds of burst stamps. Every later stretch takes its rate from the whole stretch before it. This comes from the same section.
3. After each burst, the time rule compares the burst's stamp with the time that the stretch predicts for it. The stretch ends and a new one starts when the two differ by more than half a reading period or when the sensor's buffer overflowed. This comes from the same section.
4. Time is kept as whole reading counts and 64-bit microsecond stamps, and never as 32-bit seconds. This comes from the same section.
5. The time rule lives in the shared C library, so the laptop gives every reading the same time the watch gave it. This comes from the same section and the plan's Shared C library section.
6. No code or test assumes a rate of 112.1 readings a second, and each stretch takes its rate from the reading times. Feature 1 measured 114.33 readings a second on this board, with a drift of -80.8 parts per million over twenty minutes. This comes from the roadmap entry for feature 5 and specs/tech-stack.md.
7. The converter takes each block of about one second of readings plus 16 extra readings on each side. It fits a natural cubic spline through them with one small equation solve per axis, reads the curve at each 100 Hz moment inside the block, and throws away the extra readings. This comes from the plan's Sensor and converter section, under Converting to 100 readings a second.
8. The 100 Hz grid starts at t0 of each stretch, as the toolbox's grid does. After a gap, the curve and the grid start again. This comes from the same section.
9. The converter adds no filter. This comes from the same section.
10. The time rule and the converter use 32-bit floats for readings and curve values. They include no ESP-IDF headers, allocate no memory at run time, give every buffer a fixed size, build with -ffp-contract=off, and build as part of the plain C library on the laptop. This comes from the plan's Shared C library section and specs/tech-stack.md.
11. Converter cases with the toolbox's own conversion at 100 Hz are saved in tests/. The C converter agrees with them within 0.001 degrees per second outside window 0 of each stretch. This comes from Build order step 8 and the Repo layout section.
12. The saved converter cases run without the toolbox, so the commit checks of feature 7 can run them. This comes from Build order step 10 and specs/tech-stack.md.
13. Every comparison with the toolbox sets its conversion to 100 readings a second. This comes from the plan's Measured so far section.
14. Window 0 of each stretch is warming up, and the checks leave it out. This comes from the plan's Windows section.
15. The C unit tests use Unity and run on the laptop through CTest. The Python tests that need the toolbox use pytest in the reference venv, and new Python code follows the user's Python rules. This comes from specs/tech-stack.md.
16. Nothing in reference/ changes, and nobody retrains the detector or changes its stored numbers. This comes from CLAUDE.md and specs/tech-stack.md.

## Not covered by the project documents

Each item below is a choice that the build spec and the existing code leave open.

17. The time rule is core/reading_time.h and core/reading_time.c with the prefix rt_, and the converter is core/converter.h and core/converter.c with the prefix conv_. Each keeps its state in a struct that the caller owns, rt_state_t and conv_t, and neither file has static data that changes. On the watch the sensor task owns the time rule and the pipeline task owns the converter, as the plan's Firmware design section splits the work. Tests can run more than one converter at a time. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

18. A rate is a whole number of millionths of a reading per second, held as `uint32_t rate_uhz`. For example, 114.3302 readings a second is 114330200. A whole number lets the S line in the plan's USB recording section carry the rate exactly, because every value on that line except the detector numbers must be a whole number. The rounding changes the predicted time by less than 0.1 millisecond over a two-hour stretch. A measured rate is `floor(df * 1e12 / ds + 0.5)` in 64-bit doubles, where df is the change in first reading number and ds is the change in stamp in microseconds between two bursts. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

19. A burst gives the time rule its first reading number as a `uint64_t` counted from power-on, its number of readings, its stamp as an `int64_t` in microseconds, and the overflow flag. The predicted stamp of a burst is `t0 + (f - f0) * 1e12 / rate_uhz`, where f is the burst's first reading number and f0 is the stretch's first reading number. The interrupt fires when the buffer reaches the same fill level each time, so every stamp marks the same place in its burst as t0 marks in the first burst. The burst ends the stretch when `|stamp - predicted| > 5e11 / rate_uhz`. Both sides of the test are 64-bit doubles, which give the same result on the laptop and on the watch. The time of reading n is `t0 + (n - f0) * 1e12 / rate_uhz` microseconds as a 64-bit double, and the time of 100 Hz sample k is the whole number `t0 + 10000 * k` microseconds. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

20. A stretch with no rate sets its rate at the first burst whose stamp is at least 10,000,000 microseconds after t0. The rate runs from the stretch's first burst to that burst. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

21. A later stretch takes its rate from the first burst to the last burst of the stretch before it, when those two stamps are at least 10 seconds apart. If they are closer, the new stretch measures its own rate as in item 20. So every rate comes from at least 10 seconds of stamps. The agent decided this on 22 October 2026, and the user has not reviewed it yet. The validate stage found that this item goes beyond the build spec's words, because the build spec says that every later stretch takes its rate from the stretch before it.

22. Before a stretch has its rate, it cannot predict a stamp with its own rate. In that time a burst ends the stretch when the overflow flag is set, or when the stretch spans at least 1 second and the burst's stamp differs by more than half a period from the line through the stretch's first burst and the burst before. The half period then comes from that line too. At all times a burst also ends the stretch when its stamp is not later than the stamp before, or when its first reading number does not follow the burst before. A burst with no readings changes nothing. The agent decided this on 22 October 2026, and the user has not reviewed it yet. The validate stage found that this item goes beyond the build spec's words, because the build spec names only the half period and the overflow as reasons to end a stretch.

23. Block b makes the 100 Hz samples 100b to 100b + 99, so each block adds one second of samples and completes at most one new window. The position of sample k is `k * rate_uhz / 1e8` readings, worked out in 64-bit whole numbers. The whole part is the reading before the sample, and the remainder divided by 1e8 is worked out as a 64-bit double and then rounded to a 32-bit float. Block b uses the readings from 16 before the reading of sample 100b, but not before reading 0, to 17 after the reading of sample 100b + 99. A block is made only when all its readings are in. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

24. At the end of a stretch, a block whose readings are not all in is dropped. A dropped block could not complete a window, because window n needs the whole of block n + 3, so no answer is lost. The toolbox ends its curve with scipy's not-a-knot end, and a natural end differs from it near the last reading. A planning run of reference/spline_test.py on 22 October 2026 showed this. The script printed a largest gap of 0.409 degrees per second, and every gap above 0.001 sat in the first 5 or the last 5 samples. Away from both ends the largest gap was 3.2e-6 in 32-bit floats, as the plan's Measured so far section says. The agent decided this on 22 October 2026, and the user has not reviewed it yet. The validate stage found that this item goes beyond the build spec's words, because the build spec does not say what happens to a part block at the end of a stretch.

25. The curve solve folds the reading period into the second derivatives, so it needs no rate. For a block of readings y0 to y(m-1), it sets M0 and M(m-1) to 0 and solves `M(i-1) + 4 M(i) + M(i+1) = 6 (y(i+1) - 2 y(i) + y(i-1))` with the Thomas algorithm. The value at fraction u between readings j and j + 1, with a = 1 - u, is `(M(j) a³ + M(j+1) u³) / 6 + (y(j) - M(j) / 6) a + (y(j+1) - M(j+1) / 6) u`. This is the same curve as natural_spline_block() in reference/spline_test.py, with the period h folded in. Every step runs in 32-bit floats. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

26. The converter accepts rates from 50 to 150 readings a second, which is 50000000 to 150000000 millionths. It keeps readings in a ring of 2048. The readings of a first stretch wait in the ring until the rate is known, and 10 seconds at 150 readings a second plus one full sensor buffer fit in it. A block holds at most 192 readings. conv_push() returns false when the ring has no free place, and the caller then ends the stretch. conv_set_rate() returns false for a rate outside the range, and that stretch then gives no samples. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

27. The converter takes the three gyroscope axes in degrees per second as 32-bit floats. The sensor task in feature 7 and replay in feature 10 turn raw counts into degrees per second. The converter does not convert the accelerometer, because the detector uses only the gyroscope. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

28. "Outside window 0" means every 100 Hz sample from sample 100 on. These are all the samples that windows 1 and later use. This is stricter than the samples from 400 on, which window 0 does not hold. Samples 0 to 99 have no limit, and the test prints their largest gap. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

29. tests/converter/make_cases.py makes the saved cases in the reference venv with fixed seeds. It writes stretches.csv with one row per stretch, readings.csv with one row per reading, and expected.csv with one row per toolbox sample. Every reading is a whole number of raw counts divided by 32, which is what the ±1024 degrees per second range gives, so it is exact in a 32-bit float. Each stretch lasts 30 seconds and goes to the toolbox as its own recording, through preprocess_imu_data with sensor "gyroscope", watch_side "left", and resampling_frequency 100. The side "left" leaves the signs unchanged, as in reference/spline_test.py. The expected values are written with the shortest text that gives back the same 64-bit value. The eight stretches are below. The agent decided this on 22 October 2026, and the user has not reviewed it yet.
    - Stretch mix_114 runs at 114330200, which is the 20-minute rate in firmware/bringup/rate_log.txt. It holds 60 background parts from 0.2 to 20 Hz at 0.5 to 2.5 degrees per second, as in reference/spline_test.py, and a tremor burst from 8 to 22 seconds at 4 to 6 Hz with 5 to 60 degrees per second on each axis.
    - Stretches mix_50, mix_100, and mix_150 hold the same kind of signal at 50000000, 100000000, and 150000000.
    - Stretch shake_clipped runs at 114330200 and holds a 5 Hz shake of 1500, 800, and 300 degrees per second on the three axes, clipped at the range.
    - Stretch noise runs at 114330200 and holds random noise with a spread of 200 degrees per second on each axis.
    - Stretch above_50hz runs at 114330200 and holds 45 Hz and 55 Hz parts of up to 100 degrees per second with a 5 Hz part of 30 degrees per second, so it checks that the converter adds no filter.
    - Stretch zeros runs at 114330200 and holds only zeros.

30. The toolbox gets the reading times of each stretch as `n * 1e6 / rate_uhz` seconds in 64-bit floats, counted from the stretch's t0 and not rounded. Rounded times would put the readings unevenly by up to half a microsecond, which moves a hard 5 Hz shake by more than 0.001 degrees per second. Times counted from t0 start the toolbox's grid at exactly 0, so np.arange gives each sample at k × 0.01 seconds. Feature 10 gives the toolbox reading times in the same way. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

31. The time rule test runs the twenty one-minute rates from firmware/bringup/rate_log.txt for twenty minutes, with each rate held for its minute. The rates are copied into the test, because feature 7 may delete firmware/bringup/. The test checks the rule and prints how many stretches it makes and how long each lasts. Each stretch except the last must last at least 60 seconds, because the plan says a stretch "is minutes long". A planning model of the rule on 22 October 2026 used the same rates with a smooth change between minutes and bursts of 11 readings. It made 6 stretches in twenty minutes, and the first five lasted 219, 156, 179, 262, and 306 seconds. So the measured drift alone ends a stretch every few minutes, and each new stretch has a window 0 that warms up. Feature 7 measures this on the watch. The agent decided this on 22 October 2026, and the user has not reviewed it yet.

32. specs/tech-stack.md records the time rule, the rate as a whole number of millionths, the converter's block, ring, and rate range, and the command that makes the saved cases. The agent decided this on 22 October 2026, and the user has not reviewed it yet.
