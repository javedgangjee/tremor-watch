# Feature 13 requirements: EDF export

## From the project documents

1. tools/export_edf.py writes a saved recording as an EDF+ file, so that other biosignal programs can open it. This comes from the EDF paragraph in the build spec's USB recording section, the build spec's repo layout, and the roadmap entry for feature 13.
2. The input is a file that `tools/watch_cli.py record` saved. It is gzip text, and each line holds the laptop's time in seconds with three decimals, a tab, and one line from the watch. A line whose text starts with `> ` is a command or a note from the laptop. This comes from the Saved recordings section of core/recording_format.md.
3. The signals are the 100 Hz gyroscope samples that `build/core/replay --recording FILE --samples OUT` makes, which are the samples the detector used. The watch's own rate of about 114.35 readings a second changes from stretch to stretch, so it does not fit EDF's fixed number of samples in each data record. This comes from the EDF paragraph and the roadmap entry.
4. Sample k of a stretch lies at t0 + 10000 × k microseconds on the watch's timer, where t0 is the stamp of the stretch's first burst. This comes from rt_sample_time_us() in core/reading_time.h and core/window.h.
5. Each window's answer, each face change, and each dose become EDF+ annotations. This comes from the EDF paragraph and the roadmap entry.
6. A gap between stretches or after lost lines stays a gap, with the discontinuous EDF+ form, and no samples are made up to fill it. This comes from the EDF paragraph and the roadmap entry.
7. The tool reads saved files only and never opens the watch's port, so tools/watch_cli.py stays the only program that talks to the watch. This comes from the EDF paragraph and the roadmap entry.
8. The tool reads the lines with the rules of core/recording_format.md. It skips every line before the first B line, every `> ` line, and every line that is not a record line. A line that starts with a record letter and a comma but breaks its pattern counts as a bad line. A B line with the same boot ID is a repeat after a drop, and a new boot ID starts a new boot. The last S line of each stretch number holds. A W line with an empty window is a sensor fault answer. This comes from core/recording_format.md.
9. A gzip file that was cut short is read up to the cut with its last part line dropped, and the tool says so. This comes from the roadmap entry for feature 11's second round of review fixes, which made the readers handle such files.
10. The result codes are 0 for tremor, 1 for no tremor, 2 for arm moving, 3 for warming up, and 4 for sensor fault, with the names that res_name() in core/window.c gives. The face states are 0 to 4 with the names that face_name() in core/face.c gives, which are "Tremor Detected", "Rest", "Arm moving", "Waiting", and "Dose due". This comes from core/window.h, core/face.h, and core/recording_format.md.
11. The watch writes `CLOCK at_us=A offset_us=O local_us=L` when it applies a CLOCK command, where L = A + O is the local time in microseconds since 1970 at timer value A. The clock lives in memory only, so each boot has its own clock or none. This comes from take_command() in firmware/main/state_task.c and the Commands section of core/recording_format.md.
12. A gyroscope count divided by 32 gives degrees per second, and the range is ±1024 degrees per second. This comes from core/imu_units.h and the R line in core/recording_format.md.
13. Nothing in firmware/, core/, reference/*.py, viewer/, or context/ changes, and nobody retrains the detector or changes its stored numbers. This comes from CLAUDE.md and the user's instructions for this feature.

## Not covered by the project documents

Each item below is a choice that the build spec, specs/, and the existing code leave open.

14. The tool writes EDF+ with the Python standard library and numpy, and adds no runtime package. The EDF+ header is plain ASCII and the format is small. Neither MNE-Python nor edfio can write the discontinuous EDF+D form with a time for each data record, so neither can be the writer. The bytes follow the EDF+ specification at edfplus.info. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

15. The code has three parts with one job each. tools/recording_text.py reads a saved recording into lines and reads the record patterns from core/recording_format.md. read_gzip_text(), read_recording(), and record_patterns() move there from tools/compare_session.py, which imports them under the same names, so its behaviour and its tests stay as they are. tools/edfplus.py writes EDF+ bytes from a header, signal descriptions, data records, and annotations, and it knows nothing about the watch. tools/export_edf.py reads one recording's events, runs replay, builds the data records and the annotations for each boot, and holds the command line. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

16. The command is `reference/.venv/bin/python tools/export_edf.py RECORDING [--out-dir DIR] [--boot ID] [--replay PATH]`, run from the repo root after the C build. The tool needs only numpy, which the reference venv holds. `make edf FILE=RECORDING [OUT_DIR=DIR] [BOOT=ID]` brings replay up to date with `cmake --build build --target replay` and then runs the tool. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

17. The tool writes one EDF+ file for each boot that has replay samples, because each boot restarts the watch's timer and has its own clock. The file is named `<stem>_<boot ID>.edf`, where the stem is the recording's name without its suffixes, so `table.txt.gz` with boot 2565193163 gives `table_2565193163.edf`. The files go in the recording's folder, or in DIR with `--out-dir`. `--boot ID` writes only that boot, and an ID that the recording does not hold, or a boot with no samples, stops the tool. A boot with no replay samples gets no file and a log line that names it. When no boot has samples, the tool stops. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

18. The tool refuses to write over a file, as `watch_cli.py record` does. Before it writes anything it checks every output path, and when any exists it stops, names the file, and writes nothing. It builds each file's bytes in memory, opens the path in exclusive create mode, and removes a part file when the write fails. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

19. The tool runs replay as `replay --recording - --samples TMP` on the recording's text lines without the laptop time, as compare_session.py does, and reads two things. The samples file gives boot, stretch, sample number, and the three axes in degrees per second as 32-bit floats. The window rows on the standard output give each replay stretch's t0. A replay stretch is a segment of the EDF file. Its samples must run from 0 up with no hole and must be a whole number of 100, and the tool stops with a message that names the boot and stretch when they do not. replay writes samples only from complete windows, so every stretch it writes holds 400 + 100 × (windows - 1) samples. A boot ID that comes back after a different boot stops the tool, because replay's samples name only the boot ID. replay's summary line goes to the log. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

20. A data record lasts 1 second and holds 100 samples of each axis. Data record j of a segment starts at t0 + j × 1e6 microseconds of that replay stretch. Every segment holds a whole number of seconds, so no sample is dropped and none is made up when the records are built. The samples that never reach the file are the ones replay never makes. A stretch shorter than 4 seconds plus the converter's margin gives no samples, and at the end of each stretch the readings after its last complete window are not in the file, which is less than 1 second of samples plus the 16 extra readings the converter needs. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

21. The reserved field reads EDF+C when each data record starts exactly 1 second after the one before, in whole microseconds, and EDF+D otherwise, as the EDF+ specification requires. The data records follow in time order. When a segment starts before the end of the segment before it, the tool stops with a message, because that would mean a fault in replay. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

22. The file holds four signals in this order. The first three are labelled "Gyroscope X", "Gyroscope Y", and "Gyroscope Z", with the transducer "QMI8658 gyroscope", the unit "deg/s", the prefiltering "None. Resampled to 100 Hz by cubic spline", and 100 samples in each data record. The fourth is "EDF Annotations", with digital minimum -32768 and maximum 32767, physical minimum -1 and maximum 1, and spaces in its other fields. The accelerometer is not exported, because replay gives no accelerometer samples. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

23. The gyroscope signals have physical minimum -1024 and maximum 1023.875 and digital minimum -32768 and maximum 32764. 1023.875 is 32764 / 32, which is the largest whole multiple of 1/32 below the gyroscope's top that fits the header's 8 characters, because 32767 / 32 = 1023.96875 needs 10. So each digital step is exactly 1/32 degree per second, the same as one raw count, and a reader gets digital / 32 with no rounding. The tool writes round(32 × x) with numpy's round half to even and clips it to -32768 to 32764. A sample from -1024 to 1023.875 is off by at most 1/64 = 0.015625 degree per second, because replay's spline samples lie between the 1/32 steps. A sample outside that range is clipped to the end of the range, and the log gives the number of clipped samples for each boot. Only the raw counts 32765 to 32767 and spline overshoot past the range clip. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

24. The start time comes from the boot's first line `CLOCK at_us=A offset_us=O local_us=L` that fits `^CLOCK at_us=(-?\d+) offset_us=(-?\d+) local_us=(-?\d+)$` and has L = A + O. The local time of timer value t is t + O microseconds since 1970. The `> CLOCK` command line with its laptop time is not used, because the laptop time only says when the laptop handled the line, while the watch's CLOCK line gives the exact timer value at which it set the clock. A CLOCK line that breaks the pattern or the sum is skipped and counted in the log. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

25. With a clock, the file start is the local time of the first data record rounded down to the whole second. The header's startdate and starttime give that second as dd.mm.yy and hh.mm.ss, and the first data record's time-keeping TAL gives the fraction, as in +0.658776. The recording field begins `Startdate dd-MMM-yyyy` with the English month in capitals. For a year after 2084 the header's yy is the text `yy`, as the EDF+ specification asks. Without a clock, the header gives 01.01.85 and 00.00.00, the recording field begins `Startdate X`, and the file start is the timer value of the first data record, so its time-keeping TAL is +0. The log says the boot has no clock. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

26. The header holds no personal data. The patient field is `X X X X`. The recording field is `Startdate <date or X> X X Tremor_log_watch boot_<boot ID> firmware_<version>`, where the version comes from the B line. Every header field is printable ASCII from 32 to 126, left aligned, and padded with spaces, and a value that does not fit its field stops the tool. The header's version is 0, the number of bytes in the header is 256 × 5 = 1280, the number of data records is the real count, and the data record duration is 1. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

27. Every onset and duration in a TAL is written from whole microseconds as decimal text with up to 6 decimals and no trailing zeros, with a leading `+` or `-` for the onset, as in +12.345678, -0.25, and +3. No float rounds a time. An onset is the event's timer value minus the file start, so an event before the file start has a negative onset, which the specification allows. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

28. The annotations are these, with ASCII texts.
    - Each W line with a window that is placed by the viewer's rule of feature 12 requirement 18 gives one annotation. Its onset is t0 + n × 1e6 microseconds, where t0 comes from the last S line of its stretch in the same boot, and its duration is 4 seconds, which covers the samples 100n to 100n + 399 that the detector read. Every placed answer is written, whatever its code from 0 to 3. The texts are "Answer tremor", "Answer no tremor", "Answer arm moving", and "Answer warming up". When two W lines give the same stretch and window, the last one holds. A W line whose stretch has no S line in its boot is not placed and is counted in the log.
    - A W line with code 4 is a sensor fault answer. It has no time, and the watch writes it with no window, so it is not written even when a window is given, and the log counts it.
    - Each F line gives "Face " and the state's name from requirement 10 at its time, with no duration.
    - Each D line gives "Dose taken for HH:MM" at its time, where HH:MM is the local time of its second value, or "Dose taken with no dose time" when that value is empty. It has no duration.
    - Each stretch number of the boot's S lines gives "Stretch N starts" at the t0 of its last S line, with no duration.
    The agent decided this on 2026-10-28, and the user has not reviewed it yet.

29. Each annotation goes in the data record that starts last at or before its onset, so it lies in the record that covers it, or in the record before a gap. An annotation before the first record goes in the first record. Each record's annotation signal starts with its time-keeping TAL `+<onset>` followed by bytes 20, 20, and 0, then holds one TAL for each annotation in time order, each ending with bytes 20 and 0. The rest is filled with byte 0. The annotation signal's number of samples is the largest number of bytes any record needs, rounded up to an even number and halved. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

30. The tool never crashes on a bad file. It stops with exit code 1 and one plain log line when the file is missing, when a `.gz` file is not gzip, when the file holds no B line, when replay is missing or fails, when an output file exists, and in the cases of requirements 17, 19, 21, and 26. It writes nothing in those cases. A file that was cut short is exported with a warning. On success it exits with code 0 and logs each file with its records, its form, its start, its annotation counts by kind, and its counts of clipped samples, windows not placed, and sensor faults. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

31. The tests read the files back with edfio 0.4.18, which is written apart from this tool and is the library MNE-Python uses to export EDF. It is pure Python, needs only numpy, has an Apache 2.0 licence, and came out on 2026-10-01. It reads EDF+D, gives the header fields, the digital and physical samples, the annotations, and whether the file is continuous. It does not give each data record's start, so the tests also read the time-keeping TALs from the raw bytes with their own small reader. edfio is a test-only requirement and goes in reference/requirements.txt, where pytest already sits, so the CI python job installs it. pyedflib 0.1.42 refuses EDF+D files and has no wheel for Python 3.13 on the Mac, and MNE-Python 1.13.2 reads EDF+D as if it were continuous and pulls in many packages, so neither is pinned. The validate stage opens EDF+C and EDF+D files with both in a throwaway venv. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

32. MNE-Python 1.13.2 places the data records of an EDF+D file back to back, so its times after a gap are wrong, and it drops annotations past the end of the joined data. README.md says so. EDFbrowser and edfio keep the gaps. A boot with no gap gives an EDF+C file, which every reader places correctly. The agent decided this on 2026-10-28, and the user has not reviewed it yet.

33. specs/tech-stack.md records the tool, its command, its venv, the Makefile target, the helper modules, and edfio as a test-only package. README.md gains a short section on exporting a recording. The agent decided this on 2026-10-28, and the user has not reviewed it yet.
