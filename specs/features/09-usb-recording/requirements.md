# Feature 9 requirements: USB recording and commands

## From the project documents

1. The USB task writes the recording and reads the laptop's commands. When no laptop is plugged in, it drops the recording lines. This comes from the plan's Firmware design section and Build order step 15.
2. The watch writes one line of comma-separated text per record over its built-in USB port. Every value is a whole number except the three detector numbers. This comes from the plan's USB recording section.
3. A B line marks a boot. It holds the random boot ID, the reset cause, the firmware version, and the table hash. The table hash is DET_MODEL_SHA256 from core/detector_tables.h, which is the model file's SHA-256 hash. This comes from the USB recording, Firmware design, and Shared C library sections and the roadmap entry for feature 9.
4. An S line starts a stretch. It holds the stretch number, the first reading's number, t0 in microseconds, the rate, and the gyroscope range. The rate is the whole number of millionths of a reading per second that the time rule holds. This comes from the USB recording section, the roadmap entry for feature 9, and requirement 18 of feature 5.
5. A T line records a burst. It holds the first reading's number, the number of readings, and the burst stamp in microseconds. This comes from the USB recording section.
6. An R line records one reading. It holds the reading's number and the raw counts of the three gyroscope axes and the three accelerometer axes. This comes from the USB recording section.
7. A W line records one answer. It holds the stretch number, the window number, the result code, the probability, the low-frequency sum, and the peak frequency. The result codes are 0 to 4 from core/window.h. This comes from the USB recording section and requirement 24 of feature 6.
8. An F line records a face change. It holds the time in microseconds and the new state, which is 0 to 4 from core/face.h. This comes from the USB recording section and requirement 28 of feature 6.
9. A D line records a dose taken. It holds the time in microseconds and the scheduled dose time it answers, which dose_took_it() gives. This comes from the USB recording section and requirement 32 of feature 6.
10. The laptop sends commands over the same port. One command sets the clock with the time in UTC and the local offset. Another sets the dose schedule, another starts a new session, and another turns the tone on or off. The clock command sets the dose clock with dose_set_clock(), and the new session command calls sess_new_session(). This comes from the USB recording section and the roadmap entry for feature 9.
11. Until the clock is set, the dose schedule stays off. This comes from the USB recording section.
12. The schedule has one medicine name and up to six local clock times a day. A dose time becomes due at that clock time, the circle shows Dose due, and the due state ends when fifteen minutes pass. This comes from the plan's Dose schedule section.
13. The dose schedule and the tone setting live in the chip's settings store, so they survive a restart. Answers and doses stay in memory, and the watch writes no results to flash. This comes from the Firmware design section.
14. A restart starts a new session, and the watch writes a boot line with a random boot ID and the reset cause to the recording. This comes from the Firmware design section.
15. core/ holds the recording line format and the recording format document. This comes from the plan's Shared C library and Repo layout sections.
16. The USB task is the only writer on the port that carries the recording. Feature 7 found that ESP-IDF's own log lines reach the serial port from other tasks, and that printf goes to UART0 at 115200 baud as the main console with the USB Serial/JTAG port as the second console. This feature must check that the port can carry the full recording. This comes from the roadmap entry for feature 9.
17. Feature 7 did not test the rule that lines drop when no laptop is plugged in, so this feature tests it. This comes from the roadmap entry for feature 9.
18. tests/firmware/table_run.py and tests/firmware/pipeline_run.py read the lines of features 7 and 8. This feature keeps those lines or updates the scripts. This comes from the roadmap entry for feature 9.
19. If this feature makes a task format recording lines, it measures the free stack of that task again. This comes from the roadmap entry for feature 9.
20. core/ includes no ESP-IDF headers, allocates no memory at run time, and builds with -ffp-contract=off on the laptop and the watch. This comes from the Shared C library section and specs/tech-stack.md.
21. Nothing in reference/ changes, nobody retrains the detector or changes its stored numbers, and no code or test assumes a rate of 112.1 readings a second. This comes from CLAUDE.md and the roadmap entry for feature 5.

## Not covered by the project documents

Each item below is a choice that the build spec and the existing code leave open.

22. The firmware has only the build spec's four commands. The roadmap mentions a test command that would force a stretch end through the end request queue. That command goes beyond the build spec, and the user's instructions for this unattended run on 23 October 2026 say to leave it out. So the gap path with face_gap() and the sensor task's side of the end request stay untested on the watch. The laptop tests of features 6 and 8 cover both. The user decides whether that is enough or whether feature 12's wrist test must show them.

23. The USB task writes to the USB Serial/JTAG port through ESP-IDF's usb_serial_jtag driver, with a send buffer of 4096 bytes and a receive buffer of 512 bytes. No task writes to stdout. The firmware turns the second console off with CONFIG_ESP_CONSOLE_SECONDARY_NONE, so ESP-IDF's own log lines and its crash text go only to UART0 at 115200 baud, and UART0 does not reach the USB port. This also stops the recording from going to UART0, which carries about 11,500 bytes a second, while the recording and the diagnostic lines need about 4,500. The chip's ROM still writes its boot text to the USB port before the firmware starts, so a reader skips every line before the first B line. A crash shows in the recording as a new boot with its reset cause. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

24. The USB task puts each line into the driver's send buffer with no wait. The driver takes a whole line or none of it. A line that does not fit is dropped and counted, so a laptop that is gone, asleep, or not reading never holds up the USB task or any other task. The task does not use usb_serial_jtag_is_connected(), because that function says only whether the cable carries USB frames, not whether a program reads the port. After a drop, the next line that fits first brings the B line and the latest S line again, so a recording that starts or restarts in the middle of a session still names its boot and its stretch. Lines that sat in the send buffer while nobody read come out first. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

25. The sensor task sends the USB task a copy of each burst part through a new record queue of 32 items, with no wait. A record_msg_t holds the rt_burst() flags, the stretch number and rate, the stamp, the first reading's number, the part's count, the whole burst's count, and the raw counts of up to 16 readings. The USB task writes the S, T, and R lines from it. The state task writes the W and F lines, and later the D line, through the line queue. The pipeline task writes no recording line. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

26. The lines have these exact fields, in this order, with no spaces. B is `B,<boot_id>,<reset_cause>,<version>,<hash>`. S is `S,<stretch>,<first>,<t0_us>,<rate_uhz>,<range_dps>`. T is `T,<first>,<count>,<stamp_us>`. R is `R,<n>,<gx>,<gy>,<gz>,<ax>,<ay>,<az>` with the raw counts. W is `W,<stretch>,<window>,<code>,<prob>,<below>,<peak>`, where the probability and the low-frequency sum use `%.17g` and the peak uses `%.9g`, as the ANSWER line does, so each value reads back as the same number. A sensor fault answer has no window, so its W line leaves the window and the three numbers empty, as in `W,3,,4,,,`, and its stretch is the pipeline task's current stretch. F is `F,<time_us>,<state>`, where the time is the timer value when the state task changed the shown state, which is the at_us of the FACE line. D is `D,<time_us>,<answers_local_us>`, where the second value is local time in microseconds since 1970 and is empty when dose_took_it() answers no scheduled time. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

27. The S line of a stretch goes out before the stretch's first T line. When the time rule has no rate for the stretch yet, as in the first stretch after power-on, the S line gives rate 0. When the time rule sets the rate, the USB task writes the S line again with the same stretch number, first reading, and t0 and with the rate. A reader takes the last S line of each stretch number. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

28. The boot ID is a 32-bit number from esp_random() in decimal. The reset cause is the number that esp_reset_reason() gives, as listed in ESP-IDF v6.1's esp_system.h. The firmware version is a whole number, FIRMWARE_VERSION in firmware/main/tasks.h, which is 9 in this feature and which each later feature that changes the firmware sets to its own number. The hash is the 64 hexadecimal digits of DET_MODEL_SHA256, which is the one value in the recording that is not decimal. firmware/main/CMakeLists.txt reads it from core/detector_tables.h at configure time and stops the build if it is not 64 hexadecimal digits, because only detector.c may include that header. The USB task writes the B line first, before START. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

29. The diagnostic lines of features 7 and 8 stay with their fields, and new fields go at their ends, so table_run.py and pipeline_run.py stay unchanged. A diagnostic line starts with an upper-case word of at least three characters and has no comma in its first word, so a reader tells it apart from a record line. The new diagnostic lines are SETTINGS, CLOCK, and SESSION. TONE gains `enabled=<0|1>`, SENSOR_MINUTE gains `record_drops=<n>`, STATE_MINUTE gains `clock=<0|1> schedule=<count> due=<0|1> doses=<n> tone=<0|1>`, and USB_MINUTE gains `port_drops=<n> restarts=<n> bytes=<n> commands=<n> bad_commands=<n> stack_free=<bytes>`. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

30. A command is one line of at most 127 characters that ends with a newline, and a carriage return before the newline is allowed. The commands are `CLOCK,<utc_us>,<offset_min>`, `SCHEDULE[,<name>[,<minute>...]]`, `SESSION`, and `TONE,<0|1>`, in upper case. A whole number is an optional minus sign and 1 to 19 digits. The UTC time lies from 1 January 2020 to before 1 January 2100, and the offset lies from -720 to 840 minutes. A schedule minute is a minute of the local day from 0 to 1439, and a schedule holds at most 6. `SCHEDULE` with no fields turns the schedule off and clears the name. An empty line gets no answer. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

31. The watch answers each command with one A line, `A,<command>,<result>`. The command numbers are 0 for an unknown command, 1 for CLOCK, 2 for SCHEDULE, 3 for SESSION, and 4 for TONE. The results are 0 for done, 1 for an unknown command, 2 for a bad format, 3 for a refused value, 4 for a setting that was applied but not stored, and 5 for a busy watch. The A line is a record line beyond the build spec's seven. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

32. The USB task reads the commands, parses them with rec_parse_command() from core/record.h, and stamps each with the timer value at its newline. It answers a bad command itself. It sends a good command to the state task as a new kind of state message, with no wait, and it answers 5 when the queue is full. The state task applies the command and answers it. The clock command sets the dose clock's offset to the UTC time plus the local offset minus the stamp, so the laptop's latency does not move the clock. The clock lives in memory only, so a restart leaves it unset until the next clock command. The firmware does not use the board's clock chip. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

33. The settings store is ESP-IDF's NVS in the nvs partition that the firmware's partition table already has. firmware/main/settings.c is the only file that writes it. It uses the namespace "tremor" with the key "schedule", a blob of a version byte and a dose_schedule_t, and the key "tone", one byte. With nothing stored, the schedule is off and the tone is on, because the build spec says that a laptop command can turn the tone off. main.c calls nvs_flash_init() before any task starts, and it erases and starts the store again only when ESP-IDF asks for that. At start the state task loads both settings and writes a SETTINGS line. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

34. A medicine name has 1 to 20 characters, and each is a letter, a digit, or one of `-`, `.`, `/`, and `+`. A space or a comma would break the line format, and the face's font holds these characters. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

35. The state task keeps the tone setting and writes it in the SETTINGS, TONE, and STATE_MINUTE lines. Feature 11 plays the tone and uses the setting. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

36. The line format and the command parser live in core/record.h and core/record.c with the prefix rec_, so the laptop tests them and feature 10 can use them. Each line function writes one line with no newline into the caller's buffer and returns its length, or 0 when the line does not fit. The functions use snprintf() from the C library, because the W line needs it for the three detector numbers. The rule that core/ allocates no memory covers core's own code, and the library check finds no heap call in core/. The C library's snprintf() is outside that check, and the state task already used it for doubles in feature 8. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

37. Nothing calls dose_took_it() until feature 11 adds the "Took it" button. So this feature writes the D line format in core/ and tests it on the laptop only, and feature 11 sends the D line from the state task. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

38. Three scripts check the watch. tests/firmware/record_run.py runs the recording for 30 minutes with no command and judges it with the pass checks of pipeline_run.py and its own. tests/firmware/command_run.py sends every command, restarts the watch, and waits for a dose to become due and to end, which takes about 22 minutes. tests/firmware/drop_run.py closes the port for 60 seconds and opens it again without a reset, which takes about 4 minutes. Each saves its log as gzip text and writes a report, and the validate stage commits both. The 30-minute log is about 3 MB as gzip, and feature 10 can use it to test replay. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

39. A real unplug turns the watch off, because the power chip reported no battery in feature 7. So the automated drop check closes the port with the cable in, and a manual check with a battery fitted waits for the user. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

40. specs/tech-stack.md records the console change, the usb_serial_jtag driver, core/record.h, core/recording_format.md, the settings store, and the three script commands. The agent decided this on 23 October 2026, and the user accepted it on 27 October 2026.

## Fixes after review

Each item below is a fix that a code review on 27 October 2026 found. Nothing could be tested on the watch at the time.

41. A text line holds up to 639 characters, which is LINE_CHARS in firmware/main/tasks.h, so a line_t is 640 bytes. Before this fix the limit was 319 characters, STATE_MINUTE reached 318 in tests/firmware/face_log.txt.gz, and vsnprintf() cut a longer line with no sign. With every count at 10 digits STATE_MINUTE needs about 550 characters, and every other line needs less. The 48 items of the line queue now take 30,720 bytes of PSRAM in place of 15,360, and each usb_send() call puts 640 bytes on its caller's stack. usb_send() and the USB task's own START and USB_MINUTE lines check the length that vsnprintf() gives. A cut line would end in a value that still reads as a number, so a line that does not fit goes out as `LINE_CUT word=<first word> chars=<length it needed>` in its place. A rec_ function from core/record.h that returns 0 because its line does not fit is counted too, and that line does not go out. USB_MINUTE gains `line_cuts=<n>` at its end, which counts both kinds since boot. The user asked for this fix on 27 October 2026. It has not run on the watch yet.

42. The judges in tests/firmware/ read the firmware version from each log's B line and apply that version's rules. A run with the watch still needs the B line to give FIRMWARE_VERSION from firmware/main/tasks.h. With `--log-only` a judge takes the version from the log's first B line, refuses a version it has no rules for with exit code 1 and no report, and names the version in its report. record_run.py and command_run.py know versions 9 and 11, whose checks are the same. face_run.py and tap_run.py know version 11 only, because version 9 had no face. Commit 7f6b90e swapped the looks of Rest and Arm moving on 25 October 2026 and kept version 11, so face_run.py accepts either set of looks in a saved log of version 11, as long as every view follows one set, and it names the set in its report. A run with the watch needs the looks of the firmware now. A judge also reads a gzip log that was cut short up to the cut, drops a last part line, and says so in its report. Before this fix the judges compared every log with the FIRMWARE_VERSION of the moment, so the committed reports of the version 9 logs and the face log no longer came out again from their logs. The user asked for this fix on 27 October 2026.
