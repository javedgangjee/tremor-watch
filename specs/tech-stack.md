# Tech stack

## Hardware

- The watch is the Waveshare ESP32-S3-Touch-AMOLED-2.06.
- The screen is a 410 by 502 AMOLED touch screen, and it stays on for the whole session.
- The IMU is the QMI8658. It uses rate code 0x06 with the gyroscope and the accelerometer both on, and the gyroscope range is ±1024 degrees per second. The datasheet gives 112.1 readings a second for this code, but feature 1 measured 114.33 on this board over twenty minutes, with a drift of -80.8 parts per million. Feature 7's 30-minute table run measured 114350493 and 114351161 millionths of a reading per second with the time rule, which is about 180 parts per million above feature 1's 114330200.
- The board has a clock chip, a battery gauge, and an audio codec. It has no vibration motor and no Bluetooth in use.

## Watch firmware

- The firmware is written in C with ESP-IDF v6.1. Its version macros give ESP-IDF v6.1.0. Waveshare tests its examples on v5.5.5 and v6.0.2 only, so a build problem in a Waveshare example may come from the version.
- The firmware starts from Waveshare's repo github.com/waveshareteam/ESP32-S3-Touch-AMOLED-2.06 at commit 30f3b23b3d4bb38d32f7d0cddffb66759668a855. It uses the board support package waveshare/esp32_s3_touch_amoled_2_06 at version 2.0.0 and the QMI8658 driver waveshare/qmi8658 at version 2.0.2. The screen task starts the display with bsp_display_new() and lvgl_port_add_disp() and the touch with bsp_touch_new() and lvgl_port_add_touch(). It does not call bsp_display_start(), because that function in version 2.0.0 adds the SH8601 panel as an RGB panel and corrupts the heap.
- The face uses LVGL 9.5.0, which is the version in Waveshare's LVGL example for this board.
- The font is Red Hat Display bold, converted for LVGL at 28, 40, 56, and 96 pixels only. The font file is fonts/Proportional/RedHatDisplay/ttf/RedHatDisplay-Bold.ttf of tag 5.0.0 of github.com/RedHatOfficial/RedHatFont, which is commit 6bb1048a6402b0076ea04f42951ec66263cd1437. lv_font_conv 1.5.3 converts it through npx with 4 bits a pixel, no compression, and no kerning. The fonts are stored uncompressed because LVGL 9.5.0 unpacks compressed letters through one shared state, and the face's two drawing threads overwrote each other's state and drew stripes through the letters. The 28, 40, and 56 pixel fonts hold the printable ASCII characters, and the 96 pixel font holds only the digits, the colon, the dash, and the space.
- The command `reference/.venv/bin/python tools/gen_face_assets.py` makes the fonts and the icons in firmware/main/assets/ and the font measures in core/face_metrics.h, and the output is committed. It checks the font file's SHA-256 hash, and the same run gives the same bytes. Case 48 of tests/tools/test_gen_face_assets.py checks that the committed icon files and core/face_metrics.h equal what the tool makes, and it needs no npx. The font file, its OFL.txt, and Lucide's licence sit in firmware/main/assets/.
- The layout, colours, and icons come from the design file context/Tremor Watch Light.html, with the changes that the plan's Watch face section lists. The design's colours are #111315 for text, #5C6265 for second-level text, #1B2E42 for Tremor, #3F2559 for Dose due, #173A28 for the "Took it" button and Logged, and #C9CDD0 for empty blocks. The face keeps the design's Dose due purple #3F2559, which the user chose on 2026-10-23. Feature 11 adds #2A7242 for the filled Arm moving circle, the outline #26292B for Rest, and the outline #5C6265 for Waiting. The user swapped the Rest and Arm moving looks on 2026-10-25, and the face calls the No tremor state Rest. The background is #F6F3EE on Home, Medication, and Logged, and pure white #FFFFFF on Session and Status, which the user chose on 2026-10-28. look_bg() in core/look.h gives each screen's background. The cards are white. The face does not use #C9CDD0. core/look.h holds every colour.
- The icons in the design file are Lucide icons. The face uses Lucide 0.469.0, drawn by tools/gen_face_assets.py as 88 pixel images with the A8 colour format, so LVGL colours them.
- The firmware has five tasks, which are sensor, pipeline, state, screen, and USB. They talk through queues, and only the screen task uses LVGL.
- firmware/main/tasks.h names each task's core. The sensor and pipeline tasks run on core 1, and the state, screen, and USB tasks run on core 0. The state task and the screen task must share a core, and a static assert in tasks.h holds them together. The screen task pauses the scheduler to keep the state task out between its queue test and its SCREEN_VIEW line, and on ESP-IDF that pause holds only on the calling core.
- firmware/ holds the ESP-IDF project for the watch, and the five tasks live in firmware/main/. firmware/bringup/ stays as feature 1's record.
- The power driver is an unchanged copy of XPowersLib from Waveshare's examples/esp-idf/01_AXP2101/components/XPowersLib/ in firmware/components/XPowersLib/.
- The IMU raises its buffer interrupt on INT1, which the board wires to GPIO21.
- The GPIO interrupt service runs from IRAM, so the INT1 stamp stays on time while the settings store writes to flash with the cache off. The touch pin shares the service, so the screen task's on_touch() calls the LVGL port's touch handler only while the cache is on and otherwise leaves it for the next screen round. Every settings store call comes from the state task on core 0, the core of the GPIO interrupt.
- Each of the five tasks joins the task watchdog. CONFIG_ESP_TASK_WDT_PANIC is set with a timeout of 5 seconds, so a task that stops checking in restarts the chip.
- A text line holds at most LINE_CHARS, which is 639 characters. A line that does not fit is replaced by a LINE_CUT line and counted in USB_MINUTE's line_cuts.
- The console is UART0 at 115200 baud, and the firmware has no second console, because CONFIG_ESP_CONSOLE_SECONDARY_NONE is set. ESP-IDF's own log runs at level INFO and goes to UART0 only, and so does its crash text. The USB task also removes the ROM printf's channel to the USB Serial/JTAG port at its start, so ESP-IDF's early log and its log from interrupts stay on UART0 too. The chip's ROM still writes its boot text to the USB port before the firmware starts, so a reader skips every line before the first B line. Flashing and the reset by script still work over the USB port.
- The USB task is the only writer on the USB Serial/JTAG port, and no task writes to stdout. It uses ESP-IDF's usb_serial_jtag driver with a send buffer of 4096 bytes and a receive buffer of 512 bytes. Feature 9's 30-minute table runs measured about 4,400 bytes and 127 lines a second for the recording and the diagnostic lines.
- The USB task puts each line into the send buffer with no wait, and the driver takes a whole line or none of it. A line that does not fit is dropped and counted, so no task waits on a laptop that is gone or not reading. After a drop, the next line that fits first brings the B line and the latest S line again.
- The B line gives the firmware version as FIRMWARE_VERSION in firmware/main/tasks.h. Feature 9 set it to 9, and each later feature that changes the firmware sets it to its own number. Feature 11 set it to 11. The review fixes of 2026-10-27 changed the firmware after feature 11's merge and kept 11, so a B line with version 11 does not say whether a watch has those fixes. A second round of review fixes on the same day set it to 12, because it added fields to the minute lines, the LINE_CUT line, and the task watchdog. The white Session and Status backgrounds of 28 October 2026 changed the firmware and kept 12.
- The sensor task sends the USB task a copy of each burst part through a record queue of 32 items in PSRAM, with no wait. The queue lives in PSRAM, because the display's transfers need the internal memory that it would take.
- Each display transfer needs a block of about 82 KB of internal memory. Since feature 11 the line queue, the sensor queue, and the screen queue live in PSRAM too, and the screen task makes malloc() put every new block in PSRAM before it starts the display, so LVGL's own allocations stay out of internal memory.
- The screen task owns LVGL, the ES8311 audio codec, and the BOOT button on GPIO0. It runs a round every 20 milliseconds. The state task sends it a view_t from core/view.h through the screen queue of 4 items, and the screen task sends each "Took it" tap to the state task. firmware/main/face_draw.c builds the face, and firmware/main/tone_out.c plays the tones through bsp_audio_codec_speaker_init() at 16000 samples a second.
- The dose schedule and the tone setting live in ESP-IDF's NVS in the nvs partition. The namespace is "tremor", the key "schedule" holds a version byte and a dose_schedule_t, and the key "tone" holds one byte. firmware/main/settings.c is the only file that writes it. With nothing stored, the schedule is off and the tone is on. A bad stored value falls back to its default, and the other value still loads. Answers and doses stay in memory, and nothing else is written to flash.
- The dose clock lives in memory only. A restart leaves it unset until the laptop's CLOCK command sets it, and the firmware does not use the board's clock chip.
- ESP-IDF loads with `. ~/.espressif/tools/activate_idf_v6.1.sh`, because the plain export.sh fails on this laptop unless IDF_TOOLS_PATH is `~/.espressif/tools`.
- The pipeline task asks the sensor task to end a stretch through a queue of one stretch number. It asks when a stretch loses readings, loses its first message, or fills the converter's ring. The sensor task then ends the stretch with the overflow flag, and the STRETCH line gives reason=pipeline.
- A sensor fault answer comes when no sensor message has arrived for 2 seconds, and then once a second until a message arrives.
- The detector takes about 6.6 milliseconds a window on the chip at ESP-IDF's default -Og level, with the 64-bit scoring step in software. Inside the watch firmware it takes about 6.9 milliseconds, because the other tasks share the chip. Feature 8 measured both.
- Each answer comes about 113 milliseconds after its window's last 100 Hz sample, and feature 8's table run gave 65 to 162 milliseconds from window 10 on. The wait comes from the converter, which needs 16 extra readings after each block, and from the bursts of 11 readings.
- firmware/detector_check/ is a separate ESP-IDF project. It runs the saved windows of tests/detector/ on the chip, so the chip's numbers can be checked with the rule of tests/detector/test_detector.c.

## Shared C library

- The library in core/ holds everything the watch computes. It builds as an ESP-IDF component for the watch and as a plain C library on the laptop.
- core/CMakeLists.txt also registers core/ as the ESP-IDF component core, with the same flags as the laptop build. It lists the core sources once, and the ESP-IDF build, the laptop library, and the laptop warning flags all use that list.
- core/imu_units.h holds the gyroscope's unit rule. A raw count divided by 32 gives degrees a second at the range of plus or minus 1024 degrees a second.
- It includes no ESP-IDF headers and allocates no memory at run time.
- It uses 32-bit floats and builds with -ffp-contract=off on both sides.
- It uses KISS FFT, which has a BSD licence and handles the 400 and 200 point sizes. The copy in core/kissfft/ is release tag 131.2.0, which is commit 7bce4153c6bc8aba2db0e889e576f9d00505cbe1 of github.com/mborgerding/kissfft, and its files stay unchanged.
- The detector runs every step in 32-bit floats except the scoring step, which runs in 64-bit doubles as the 32-bit run of plain_detector.py does.
- The detector adds its two window sums and its low-frequency sum in the order numpy 2.5.4 uses. numpy adds blocks of up to 128 values in eight running sums and splits longer arrays in two. It multiplies the coarse spectrum by the float 1 / (sum of the window), because numpy divides that way. These two choices give the same floats as plain_detector.py, so a numpy update in the reference venv could change the last bit of a value.
- KISS FFT builds with KISS_FFT_MALLOC and KISS_FFT_FREE set as compiler options that do nothing, and det_init() builds both FFT setups in fixed static buffers.
- The detector keeps its work buffers in static memory, so only one task may call it. That task is the pipeline task.
- The generated tables are in core/detector_tables.h, and the command `reference/.venv/bin/python tools/gen_tables.py` makes them. The model numbers in it are 64-bit values, and the tables are 32-bit values.
- The laptop build includes replay, a command-line program that reads a recording or a PADS file and prints an answer for every window.
- The time rule lives in core/reading_time.h and core/reading_time.c, and the converter lives in core/converter.h and core/converter.c. The caller owns the state of each, so neither file has static data that changes. The time rule ends a stretch when a burst's stamp lies more than half a reading period from the stretch's prediction or the sensor's buffer overflowed, and every rate comes from at least 10 seconds of stamps. Requirements 21 and 22 of feature 5 add rules that go beyond the build spec's words, and the user accepted them on 27 October 2026.
- A rate is a whole number of millionths of a reading per second, held as a `uint32_t`. For example, 114.3302 readings a second is 114330200.
- Each converter block makes 100 samples at 100 Hz and fits its natural cubic spline over its readings plus 16 extra readings on each side. A block holds at most 192 readings. The converter keeps readings in a ring of 2048, and it accepts rates from 50 to 150 readings a second. At the end of a stretch it drops a block whose readings are not all in, as requirement 24 of feature 5 says. The user accepted that requirement on 27 October 2026.
- core/window.h holds the result codes and the window rule. core/share.h holds the session share and the Session screen's blocks. core/face.h holds the face state, the two-in-a-row rule, and the gap rule, which shows Waiting at once when a new stretch starts after a gap. core/dose.h holds the dose schedule and the due rule. The caller owns the state of each, so none of these files has static data that changes. On the watch the pipeline task owns the window rule, and the state task owns the share, the face, and the doses.
- core/pipeline.h holds the pipeline task's rules for the stretches, the converter, the windows, and the sensor fault answers. core/session.h holds the state task's rules, which join the share, the face, and the doses. The caller owns the state of each, so neither file has static data that changes.
- core/look.h holds the face's colours, layout, and text measures, core/screens.h the screen rules, core/view.h the texts the face draws, and core/tone.h the tone samples. core/face_metrics.h holds the font measures that tools/gen_face_assets.py makes. The caller owns the state of each, so none of these files has static data that changes.
- core/record.h holds the recording line format and the command parser, and core/recording_format.md describes the lines, the commands, and the answers. The W line writes the probability and the low-frequency sum as the shortest text that reads back as the same double, which is what the watch's picolibc gives for %.17g. The Mac's C library writes all 17 digits for %.17g, so core/record.c finds the shortest text itself.

## Reference and laptop tools

- The laptop is a Mac. It builds the code, runs the checks, sets the watch's clock and dose times, and saves recordings over USB.
- The Python reference runs in its own venv with Python 3.13, ParaDigMa 1.1.2, and scikit-learn 1.6.0. The toolbox's model file needs scikit-learn below 1.6.1.
- The pinned Python requirements live in reference/.
- The tools in tools/ are gen_tables.py, gen_face_assets.py, watch_cli.py, compare_session.py, and export_edf.py. tools/recording_text.py reads a saved recording into lines and reads the record patterns from core/recording_format.md for compare_session.py and export_edf.py, and tools/edfplus.py writes EDF+ bytes for export_edf.py and knows nothing about the watch.
- tools/watch_cli.py sets the watch's clock and dose schedule, starts a session, turns the tone on or off, and saves a recording. It needs pyserial, which the reference venv lacks, so it runs with the ESP-IDF Python at ~/.espressif/tools/python/v6.1/venv/bin/python.
- tools/compare_session.py compares a recording with replay and the toolbox and writes a session report. It needs the toolbox, so it runs in the reference venv.
- tools/export_edf.py writes a saved recording as EDF+ files, one for each boot that has replay samples. The command is `reference/.venv/bin/python tools/export_edf.py RECORDING [--out-dir DIR] [--boot ID] [--replay PATH]`, run from the repo root after the C build, and `make edf FILE=RECORDING [OUT_DIR=DIR] [BOOT=ID]` brings replay up to date and runs it. It needs only numpy and replay, and it runs in the reference venv. Each file holds replay's 100 Hz gyroscope samples with one data record a second, and the answers, face changes, doses, and stretch starts as annotations. A boot with a gap between its replay stretches gives a discontinuous EDF+D file. MNE-Python 1.13.2 places the data records of an EDF+D file back to back, so its times after a gap are wrong, and it drops annotations past the end of the joined data. EDFbrowser and edfio keep the gaps, and pyedflib 0.1.42 refuses an EDF+D file. The rules are in specs/features/13-edf-export/requirements.md.
- The tests read the EDF+ files back with edfio 0.4.18, which is a test-only package in reference/requirements.txt. It needs only numpy and has an Apache 2.0 licence.
- The Python tests in tests/ need the toolbox, so they run in the reference venv with `reference/.venv/bin/python -m pytest tests -q`.
- New Python code follows the user's Python rules. The scripts in reference/ stay as they are, because the measured results come from them. In feature 2, compare.py, rate_test.py, latency_test.py, spline_test.py, and demo_test.py changed their import line to `from plain_detector import build_tables, detect` when they moved from context/, and nothing else changed.
- reference/pads_counts.py runs the toolbox on every PADS recording. Its results in reference/results/ are pads_windows.csv, pads_counts.csv, and pads_counts.md, and they are committed as the counts the C port must reproduce.
- PADS 1.0.0 lives in data/pads/ and is never committed.

## Recording viewer

- The recording viewer in viewer/ is a small Electron app that shows a saved recording on the Mac. Its Record button starts `tools/watch_cli.py record` as a child process with an argument array and no shell, and a second press stops it with SIGINT, as Ctrl-C does. The viewer then opens the saved file. watch_cli.py is the only child process the viewer starts, and the viewer still never opens the watch's port.
- The viewer runs watch_cli.py with the Python that TREMOR_PYTHON names, or with `~/.espressif/tools/python/v6.1/venv/bin/python`, which holds pyserial. Recordings go to recordings/ at the repo root, which git leaves out, or to the folder that TREMOR_RECORDINGS names, with names of the form `tremor-YYYY-MM-DD-HHMMSS.txt.gz` from the laptop's local time.
- It uses Electron 44.7.1 and uPlot 1.6.32, which are its only two packages. viewer/package.json pins both exactly, viewer/.npmrc sets save-exact, and viewer/package-lock.json is committed. The app uses no framework, no bundler, and no TypeScript, and it runs from the repo without packaging. `npm audit` flags Electron 44.7.1 with advisory GHSA-jr5w-w6x2-84p9, fixed in 44.10.0. The viewer opens no network connection, so feature 12's validate judged that the advisory does not reach it, and the user decides whether to move.
- Node v22.22.1 and npm 11.20.0 from nvm run npm and the unit tests.
- The page follows the design in context/viewer-design/. Its colors.css, typography-spacing-fonts.css, and components.css are copied unchanged into viewer/src/renderer/design/, and viewer.css holds only the page's own layout, written with the tokens. The fonts are Red Hat Display, Libre Franklin, and IBM Plex Mono as latin woff2 files in viewer/src/renderer/fonts/, taken from Fontsource 5.3.0 on the npm registry with `npm pack`, so they add no package. The page follows the Mac's light or dark setting through theme.js, and `--theme system|light|dark` sets it. `--layout overlaid|stacked` sets the layout of the file named on the command line.
- The modules in viewer/src/lib/ read the file (read_text.js), read the line patterns from core/recording_format.md (format.js), parse the lines (parse.js), give each reading its time (timeline.js), place the windows (windows.js), and join these steps (load.js). args.js reads the command line, pixels.js checks captured colours, recorder.js runs watch_cli.py for the Record button, and chart.js holds the page's pure rules for numbers, times, ticks, answer blocks, the selection, the tremor and selection lines, and the y ranges. The page loads chart.js as a classic script. They use only Node's built-in modules, so their tests need no installed packages.
- viewer/src/main.js owns the window, the menu, the open dialog, the file reading, and the recorder, and viewer/src/capture.js runs the capture mode. viewer/src/preload.js gives the page six calls, which are openFile(), onRecording(), reportDrawn(), startRecording(), stopRecording(), and onRecordStatus(), and the page in viewer/src/renderer/ only draws and shows the record status. In the page, theme.js sets the theme, plot.js draws the uPlot charts and keeps their shared view, answer_row.js draws the Answer row and handles its keys, and viewer.js runs the rest.
- The command `npm --prefix viewer ci` installs the packages, which needs the network. The first start after it also needs the network, because Electron fetches its binary then. The command `npm --prefix viewer start -- [FILE] [--boot ID] [--capture OUT.png] [--record-for SECONDS] [--theme system|light|dark] [--layout overlaid|stacked]` starts the app. With `--capture` it draws FILE with no person, makes the window as tall as the page, saves OUT.png and OUT.json, and exits. With `--record-for SECONDS` and `--capture` but no FILE, it records for SECONDS through watch_cli.py and then draws the new file. In capture mode only, the environment variable TREMOR_CAPTURE_SELECT, which holds `STRETCH,WINDOW`, makes the page select that window before it reports. It is a test hook for the smoke suite, and other text in it exits with code 2. `make viewer-start [FILE=FILE] [BOOT=ID]` runs `npm --prefix viewer start` and first runs `npm --prefix viewer ci` when viewer/node_modules is missing or older than viewer/package-lock.json.
- The command `node viewer/scripts/make_synthetic.js` writes the made-up recording viewer/test/fixtures/synthetic.txt.gz again, and `--long OUT --minutes M` writes a long one.

## Tests and checks

- The command `build/core/replay --pads FILE` runs the C detector on one PADS recording and prints one answer for every window.
- The command `build/core/replay --recording FILE` runs the time rule, the converter, and the C detector on a recording from the watch and prints one answer for every window. FILE may be `-` for the standard input, and `--samples OUT` also writes the 100 Hz samples. The T line holds no overflow flag, so replay finds each stretch start from the S lines, and core/recording_format.md gives the rule.

- The Python tests for tools/, replay's recording input, the saved windows, and the PADS match use pytest. The cases check the place and colour of the tremor start and end lines, the dashes of the selection lines, and the shared y range of the stacked plots. Every case runs with `--theme light` unless it names a theme. It needs the installed packages and a logged-in screen, so it stays out of `make check` and CI. `make viewer-smoke [OUT=DIR]` runs it. Case 27 used to fail about once in five runs, because capture mode could save the page before the plot was drawn. Since feature 15, capture mode makes the window as tall as the page and waits two frames before it saves the page, and eleven runs in a row passed, so the race is likely gone.
- The full PADS match test needs the toolbox, so it runs before each release and not on every commit.
- The test data is PADS from PhysioNet, which holds 100 Hz gyroscope recordings in radians per second.
